## Reproducible input build

Run scripts/build-signal-runtime-inputs.sh OUTPUT [--check] on Linux using the
container image pinned in signal-runtime-inputs.yml. It verifies the exact source
checkout, builds installDist with the SHA-pinned Temurin 25 JDK, and assembles
darwin-arm64, win32-x64 and linux-x64 from SHA-pinned per-platform JRE images.
No foreign executable is run. Every JNI library is extracted from its pinned
libsignal-client-0.106.1.jar entry; no native compiler is needed.

Each archive contains signal-cli.jar, the complete lib/ closure, native/,
and jdk/ holding the prelinked JRE. Inventory comes from the staged tree.
Tree digests pin sorted file bytes and executable bits, plus in-tree symlink
targets. Windows file executable bits are normalized to zero. Archives use
sorted names, epoch timestamps, owner/group zero and timestamp-free gzip.

--check rejects any rebuilt fragment or archive differing from runtime-pin.json.
The manual workflow emits workflow artifacts only. release.yml repeats the
build and check, and uses those workflow artifacts for first-release staging.
Only release.yml's explicit publish step attaches the three archives to
FerroxLabs/murage-releases under signal-runtime-0.14.11-48a0a5e-r1.

## Offline and release staging

Local staging uses reviewed inputs on the matching target:

    node scripts/stage-signal-runtime.mjs --target linux-x64 --input INPUT

Release staging supports the reviewed workflow artifact before public assets
exist, or the exact pinned HTTPS asset after publication:

    node scripts/stage-signal-runtime.mjs --target linux-x64 --release --archive ARCHIVE

Archive bytes must match the committed sha256 before extraction. The
prelinked-jre layout copies the already pinned image, then rechecks its tree,
all application jars, JNI provenance and licences. The local JDK layout still
uses ALL-MODULE-PATH jlink. Staging never changes the pin, overwrites an existing
destination, or accepts a different host/architecture. Missing evidence blocks
staging before any command. No unsupported target may borrow another image.

The output is dist-native/signal-runtime/<target>/ outside ASAR. Temurin's
jre/lib/jrt-fs.jar is covered by the JRE tree pin; the separate application
inventory has 51 jars. No additional application jar is accepted.

## Inventory handoff

B8 owns `server/channels/signal/signal.inventory.json` surface declarations:
`{ "surfaces": [{ "kind": "card|route|search|problem|recovery|review", "id":
"registration id", "path": "repository-relative source", "why": "One line." }] }`.
Declare every card, route, search target, problem and recovery control, and
delivery review. The runtime inventory generator requires all six categories,
checks declarations against their sources and reconciles registrations in both
directions. Cards use the generated `section.name` id from `card(...)` in
`src/lib/settings-card-registry.ts` (including `idSection` overrides); every
card is also a search target through `APP_SETTINGS_ENTRIES`. Additional Signal
search entries come from `src/lib/settings-index.ts`. Routes come from
`server/index.ts`, problems from `SignalProblem`, and controls from
`SignalAction`: variants with `deliveryId` are review controls, the others are
recovery controls. Use action ids, not button labels. Source hashes make edits
require regeneration, while discovery also rejects missing declarations during
generation itself.

Staging generates a separate `signal.inventory.json` in each target's runtime,
containing the pin digest, jar identities, JRE build, JNI provenance, copied
licences, source-backed surface records, and every runtime file. B8 declarations
are required before that step can complete. `--check` compares the generated
record with the actual staged or packaged bytes and the reviewed repository pin:

```
node scripts/signal-inventory.mjs dist-native/signal-runtime/linux-x64 --target linux-x64 --check
```

General CI keeps --pin-status non-blocking while G0 is pending. The dedicated
dev/1019-signal push gate uses --assert-runtime-inputs and omits only G0-live.
RC preparation and the first release.yml job use --assert-release-pin; staging
and packaged --check steps remain unconditional and fail closed.

Offline unit tests use scripts/signal-runtime.test-config.mjs, isolated
temporary trees, synthetic bytes and an injected fake jlink runner. Synthetic
staging records never replace committed G0-live evidence.
