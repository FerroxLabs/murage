Owners: SERVER side (StepLog, engine mapping, labeler, redaction, step store, step routes): OPEN NO-OWNER, MAIN assigns. CLIENT side (StepsGroup, detail pane, settings copy): OPEN NO-OWNER, MAIN assigns. Contract between them: the `step.upsert` frame and the three routes in §5. Design owner: steps-view-design-r2. Binding inputs: SEAN-ADDENDUM.md, THRUST-RULES, GAP-CHECK-BAR, the UX bar (`swarm-b/_designs/MURAGE-UX-BAR.md`), JOINT RULING STOP-VS-REFUSAL. r1 is kept as STEPS-DESIGN-r1.md. r2 closes every High of both r1 reviews; §12 maps each finding to its fix.

**PURPOSE.** While a bot works, the owner can tell at a glance what it is doing, which step it is on and what happened, in plain words, on every engine and in every chat. One click shows the exact command and output.
**USER PROMISES.** P1: one collapsed live line per turn says what the bot is doing now and for how long, and says "Waiting for your OK" when it is waiting on you. P2: each step is one plain-English row: present tense while it runs, past tense once done. A failed step says "Failed" in red, a step you refused says "Not allowed" (not red), and the chain carries on. P3: any row opens to its Request (command or arguments) and Response (output), code-highlighted. P4: each tool call appears exactly once, and two identical calls appear as two rows. P5: secrets never show, even in the opened detail, and step output is deleted with its chat. P6: a 500+ step turn stays smooth and the disk used is bounded. P7: under No limits nothing new asks you anything; the chain only reports.

## 2. The duplicate lines: cause not proven; removed by construction
Today a line is added per **ask**, not per **tool call**, so anything that produces two asks, or two renderers, for one call doubles the line. Both reviewers doubt r1's named cause, and so do I now: a PreToolUse hook that answers "allow" normally skips the CLI's own permission ask. Candidates, in the order the builder checks them:
1. two asks reach `handleDecisionRequest` for one call (the No limits Bash hook `relayClaudeBash`, claude-bash-hook.ts:19, plus the CLI permission tool; or a Codex non-final hook allow re-asked, codex.ts:2083);
2. the step line **and** a tool chip show the same call (two renderers, same text);
3. one ask is noted twice (a replayed or re-judged request id).
**First build task (RED first).** A witness records, per `tool_use.id`, (a) every ask on the broker socket with its id and source, (b) every `handleDecisionRequest` call, (c) every transcript row written. It runs one No limits **Bash** call and one **non-Bash** call (Read) on CLI 2.1.310. Broker asks do not appear on CLI stdout, so a stdout recording is not enough. The witness names which candidate is real. Whatever it finds, the rule below removes all three. The legacy lines already stored (§10) are shown as stored, doubled or not: two real identical calls cannot be told from a doubled one after the fact.
**Rule: rows come only from engine tool items. An ask never creates a second row; it attaches to exactly one step.**
- **Engines whose asks carry the call id** (Codex `itemId`, ACP `toolCall.toolCallId`, Grok API / OpenAI-compatible where Murage itself runs the tool): exact match on that id inside the live turn.
- **Claude: exact id first.** The permission tool's schema already declares `tool_use_id` (permission-proxy.ts:119) and the PreToolUse hook input carries it, but both are dropped before the ask reaches the driver (permission-proxy.ts:178-181, claude.ts:6304). The builder forwards it on every ask kind: permission, **question** (AskUserQuestion, `ask_user`) and the hook relay. An ask with a `tool_use_id` matches its step exactly, so a question card is tied to its own row and never makes a second one.
- **Claude fallback, only when an ask arrives without the id** (the duplicate witness records whether 2.1.310 always sends it). The only link left is `callKey`, a **content** key (tool + sorted input, claude.ts:2998, 6215). It is computed for question asks too (today only for permission asks, claude.ts:5408), with the ask's short tool name mapped to the item's full name (`ask_user` ↔ `mcp__…__ask_user`). The match is **FIFO, one ask per item per source**:
  - per live turn and callKey, two queues: steps with no ask from a given source yet (in start order, non-terminal only: a finished step leaves the queue), and asks with no step yet (in arrival order);
  - an ask attaches to the **oldest non-terminal step** with that callKey that has no ask from the **same source** (`hook` = `relayClaudeBash`, `cli` = the permission tool; the hook relay adds `via:"hook"` to its ask). So hook + cli asks for one call land on one row, and two cli asks for two identical calls land on two rows;
  - an ask with no free step creates a **provisional row** at once (label from the ask's tool and input), so "Waiting for your OK" shows even if the item is late. A provisional row is a step like any other in the queue: an ask from the **other** source with the same callKey attaches to it (hook + cli before a late item → still one row). The next `item.started` with that callKey **adopts** the oldest provisional row instead of adding a row. Two asks from one source are never merged;
  - no new timer: the only wait is the driver's existing `CLAUDE_ASK_ITEM_WAIT_MS = 2000` (claude.ts:2980, owner: the Claude driver, NOLIMITS V5), which holds a No limits ask until its item is seen (2 s of readable time, 10 s wall ceiling, `CLAUDE_ASK_ITEM_WALL_MS`, claude.ts:2984). StepLog accepts either order.
  - Two identical calls running at once with one ask: the ask goes to the older row. The two rows have the same label and the same Request, so the owner cannot be misled about what is waiting; counts stay exact.
- **Witnesses:** two identical No limits Bash calls in one turn → 2 rows, each with its own approval tag; hook + cli ask for one call → 1 row, 1 tag; ask before item → 1 row (provisional, adopted); a first identical call that finished without asking and a second that asks → the ask lands on the second row; an AskUserQuestion call and an `ask_user` call → 1 row each, `waiting` while the question card is open; hook + cli asks both before a late item → 1 row.

## 3. Event model (one shape for all engines)
```ts
type StepKind = "command"|"read"|"write"|"edit"|"search"|"list"|"web_search"|"web_fetch"|"app"|"skill"|"delegate"|"browser"|"computer"|"plan"|"note"|"other";
type StepStatus = "waiting"|"running"|"done"|"failed"|"denied"|"stopped"|"no_result";
interface Step {                 // the summary row (SQLite) and the SSE frame; frame <= 512 B
  threadId: string;              // server thread id; the SSE visibility filter (sse-visibility.ts frameSubject) scopes the frame by it
  groupId: string; seq: number;  // SERVER-minted: groupId = id of the group's transcript message, seq = 0,1,2.. first-seen order in the group
  rev: number;                   // per-group update counter, for catch-up after a dropped connection
  kind: StepKind;
  label: { key: string; object?: string; app?: string };   // §4; object <= 96 B, app <= 32 B (UTF-8, cut on a code point)
  status: StepStatus; startedAt: number; endedAt?: number; waitMs?: number;  // run time = endedAt - startedAt - waitMs
  waitingFor?: "ok"|"answer";    // set while status is waiting: an Allow/Deny or wipe card, or a question card
  approval?: "no-limits"|"full-access"|"owner"|"rule"|"own-files";   // how the ask that reached handleDecisionRequest (if any) was answered
  deniedBy?: "owner"|"rule"|"no-answer"|"refused";   // "refused" = Murage refused for another reason; the footer shows the refusal's own message
  error?: string;                // first line, redacted, <= 160 B
  hasDetail: boolean; parentSeq?: number;                  // delegate nesting, one level
}
interface StepDetail { tool: string /* raw engine tool name, <= 64 chars, shown only here */; args: string; argsLang: "bash"|"json"|"diff"|"text"; output: string; outputLang: string; omitted?: { lines: number; bytes: number }; withheld?: "too-large-to-check"|"binary"|"image"|"masked-turn"|"not-kept"|"older-step" }
```
**Identity (closes the id finding).** Engine ids (`tool_use.id`, Codex `item.id`, ACP `toolCallId`, API `tool_call.id`) and provider turn ids are strings chosen by the engine or a model endpoint. They are used **only** as keys of an in-memory `Map<engineId, seq>` that lives for one turn. They are never a file name, a route segment or a storage key. The stored key is `(threadId, groupId, seq)`, all server-minted, always passed as bound SQL parameters. An engine id that repeats in a later turn meets a fresh map. An engine id that repeats **inside** a turn: same args hash → a replay, ignored (warm and resumed sessions replay `started`); different args → a new row, and the map entry moves to it. Drivers where Murage runs the tool loop itself (Grok API, OpenAI-compatible) key by their own per-turn call counter, never by the endpoint's `call_0`.
**Status rules.** A step starts `running` at `item.started` (or `waiting`/`denied` when it is created by an ask, §2). The two open states can alternate, and the five final states are never left:
`running ⇄ waiting`; `running | waiting → denied | stopped | no_result`; `running → done | failed`.
- `running → waiting`: an ask matched to this step is shown to the owner as a card. This is the normal order on Claude and ACP, where the item arrives before the ask. The outcomes of `handleDecisionRequest` (decision/types.ts:96) map as: `card` → `waiting`, `waitingFor:"ok"`; `question` → `waiting`, `waitingFor:"answer"`; `run` → stays `running`, sets `approval` only; `refuse` → `denied`.
- `waiting → running` when the card is answered Allow or the question is answered (`request.resolved`). Each wait adds to `waitMs`, so a step asked twice is still timed right.
- `→ denied` (from `running` or `waiting`) when the ask matched to the step is refused: the owner presses Don't allow (`deniedBy:"owner"`), a rule refuses (`"rule"`), the card closes unanswered (`"no-answer"`), or Murage refuses for another reason such as its open-card limit (`"refused"`, decision/implementation.ts:279; the footer shows that refusal's own message, never "your rule").
- A `denied` step is final. The engine's own error result that follows (`ok:false`) is stored as its Response and does not turn the row red. A `completed` that arrives while a step is still `waiting` (an engine that answered itself) ends the wait and applies normally.
- `stopped` is set only when the owner's Stop is **confirmed** (its close receipt exists, per the JOINT RULING). Until then the row stays `running` or `waiting`. A turn that ends with no confirmed Stop turns its open rows to `no_result`, including when a refusal row is shown for a held Stop.
- A `completed` before its `started` (Fuigo hosted tools) creates the row already final.
**Engine mapping** (drivers already emit `item.started{itemId,title,input,callKey}` / `item.completed{ok,result}`; `result` is dropped today):
| Engine | Lookup id (in-memory only) | Args | Output | Ask link | New driver work |
|---|---|---|---|---|---|
| Claude stream-json | `tool_use.id` | `tool_use.input` | `tool_result.content` text parts; `is_error` → failed; image blocks → "Image (N KB), not shown" | `tool_use_id` if present, else callKey FIFO (§2) | carry `parent_tool_use_id` on items (today sub-agent calls arrive with no parent link): they become child steps of the `Agent`/`Task` row; sub-agent text is never a note of the parent chain |
| Codex app-server | `item.id` | commandExecution `command`/`cwd`; fileChange diff; mcpToolCall `server/tool/arguments` | `aggregatedOutput`; `exitCode≠0` → failed | approval `itemId` | reasoning summary titles → notes; `outputDelta` live tail is new work (§5) |
| Fuigo / Grok ACP | `toolCallId` | `rawInput` | `rawOutput` or `content[]` text/diff; `status:"failed"` | `request_permission.toolCall.toolCallId` | none |
| Grok API / OpenAI-compat | Murage's own call counter | parsed `arguments` | the tool message Murage sends back | Murage's own gate, same counter | `use_tool` wrappers unwrapped (existing `wrappedTool`) |
**Narration rows (`kind:"note"`).** Reasoning-summary titles (Codex summary headings, the first line of an ACP `agent_thought_chunk`), plus **short interim** assistant text: one line, at most 160 chars, with another step after it in the same turn. Longer interim text stays a normal bubble and splits the chain into two groups. The closing reply is never a note. Three guards so nothing the bot said is lost: (1) while the group is collapsed and live, the newest note shows as a grey second line under the header; (2) if the turn ends with no closing reply (Stop, crash, error), the last note is shown again as a normal bubble; (3) Settings has "Fold short in-between messages into steps" (on by default; off = all assistant text stays a bubble and only reasoning titles are notes). **Folding is display only.** The interim text is stored as the normal assistant message it is today, after the same guards, so memory, speech, branches and search are unchanged; when the next step starts, the server sets one flag on it, `stepNote:{groupId, afterSeq}`, and the client draws a flagged message inside the group instead of as a bubble. Guard (2) is the server clearing that flag. Only reasoning titles are stored as `note` rows in `turn_steps`. This follows Sean's addendum over the 1020 "what the bot said stays where it was" rule; see Decisions for Sean, §13.

## 5. Storage, streaming, lifecycle and limits
**Two stores, split by what they are.**
- **Rows** (small, part of the conversation): table `turn_steps` in `messages.db`, primary key `(thread_id, group_id, seq)`, about 200 B a row. Deleted in the same transaction as the chat (`mdb.deleteThread`, message-db.ts:1573, one more `DELETE … WHERE thread_id=?`). The builder registers the table in the schema additions, `ADDED_TABLE_LIFECYCLE` and the downgrade list, as every added table is. Rows are in backups because `messages.db` is; they carry the same class of data the transcript's tool chips carry today.
- **Details** (bulky tool output; this is the first place Murage keeps it): a separate SQLite file `step-details.db` in the data folder, table `step_detail(thread_id, group_id, seq, tool, args, output, langs, omitted, withheld, bytes, at)`, with `secure_delete=ON` so deleted output does not linger in free pages. No per-step files, so no inode growth.
**Lifecycle of details.**
- **Deleted with the chat and the bot.** `deleteThreadRecord` (store.ts:2967) is the one funnel for every delete path (deleteGroup 3001, deleteGroupTask 3264, deleteBot 4913, deleteTask 6391). It calls `stepDetails.deleteThread(threadId)` right after the `messages.db` transaction. The boot deletion triage deletes rows directly (index.ts:12010 → conversation-deletion.ts:1708, not through the funnel), so step details are also registered with that module's durable pending record: a deletion it finishes at boot finishes the details too. As a backstop, a boot sweep that runs **after** the triage deletes details whose thread no longer exists. After every delete the file gets the same post-delete WAL scrub `messages.db` gets (wal-maintenance.ts: checkpoint, then prove the old bytes are gone), because `secure_delete` clears the main file only. Witness: delete a chat, a room, a task and a bot → 0 detail rows for their threads and the output bytes are in neither the file nor its `-wal`; kill between the two steps → the same after restart.
- **Global cap.** "Step details kept" in Settings (Advanced): Off · 250 MB · **1 GB (default)** · 5 GB. A one-row total is updated in the same transaction as each insert. Over the cap, the oldest details are deleted in batches of 64 until under it (O(1) amortised). The row stays and opens to "Details weren't kept" (`withheld:"not-kept"`). Off stores no details at all. Lowering the cap evicts at once.
- **Not in backups, sync, diagnostics or feedback.** `step-details.db`, `-wal` and `-shm` get explicit `excluded` entries in data-dir-inventory.ts (as `search.db` has, :157), and the snapshot's root-membership check ignores them so a turn writing during a backup cannot fail it with SOURCE_CHANGED. Restore and erase delete the file, as they do `search.db`, so after a restore rows show and details read "Details weren't kept". Details never leave the machine; a paired phone reads them live through the detail route.
- **Memory.** A live turn holds its id map and its non-final steps only; both are dropped when the turn ends, is stopped or is swept at boot. Final rows live only in SQLite.
**Routes.** All three are registered in route-policy.ts with class **`companion`** (the desktop or the proven owner's phone), never `conversation`: that class also answers local door and MCP callers, which must not read tool output. The `step.upsert` and `step.output` frames are added to the SSE frame-kind list and scoped by `threadId`, so hidden-bot and bot-to-bot scopes never receive them. All ids are bound parameters; `seq` must be a 1-6 digit integer:
- `GET /api/threads/:threadId/steps/:groupId?after=<seq>&limit=200`: a page of rows. `?sinceRev=<n>`: rows changed since `rev` n (catch-up after a dropped SSE or a sleeping phone).
- `GET /api/threads/:threadId/steps/:groupId/:seq/detail`: one detail, or `{withheld}`.
- `POST …/:seq/tail` (subscribe/unsubscribe to a running step's live tail).
**Per-step work is O(1) in turn length.** First sight: one row insert + one `step.upsert` frame (≤ 512 B; the builder asserts the size and cuts `object` first, then `error`). Each status change: one row update + one frame. End: one detail insert. The transcript holds **one** message per group: `kind:"activity"` with `tool.name` = the plain header text ("Worked for 5m 35s · 27 steps") and a new field `tool.stepsRef = {groupId, counts}`. An older client or phone build therefore shows the known one-line chip; a 1.0.22 client sees `stepsRef` and renders StepsGroup. That message is written once at group start and patched once at group end. Counts for a reload mid-turn come from the live StepLog. After a crash the end patch never ran, so boot recomputes the counts of any group left open from `turn_steps` and patches its message once ("Ended after …"). Each row also stores `search_text`, the label as words in the app's language at write time, and transcript search matches that (never the i18n key); a hit opens the group at that row (existing `forceOpen`).
**Size limits.** Args kept up to 16 KB. Output kept as head 8 KB + tail 24 KB of the **already redacted** text, cut on line boundaries, with "… 1,240 lines not shown (310 KB)". Highlighting up to 2,000 lines or 64 KB, plain monospace beyond. Binary or non-UTF-8: "Binary output (12 KB), not shown". Images: "Image (240 KB), not shown". Each turn keeps at most 8 MB of detail; later steps in that turn keep their row and read "Output not kept: this turn is very large". Each group keeps its newest 5,000 rows (a ring: inserting row n deletes row n-5000 and its detail, one indexed delete each); the list starts with "312 earlier steps not kept". Child steps of a same-turn sub-agent count toward the parent turn's caps; a helper bot's steps live in the helper's own thread under its own caps. Header counts stay exact (kept in the StepLog, written to `stepsRef.counts`).
**Live output (only where the engine streams it).** Today only Codex can (`outputDelta`, new driver work). A running step that is open shows the tail if its engine streams, otherwise "Output appears when the step finishes." The tail is built from scanned text only (§6); frames are at most 4 KB, at most 4 a second, and are sent only to connections subscribed to that step. Live tail is the last build item; the design is complete without it.
**Timers.** The client computes them from `startedAt`/`waitMs`. One shared 1 s ticker per on-screen live group. The server never sends ticks.

## 6. Privacy: redact first, then cut, then store or send
**One order, everywhere: (1) take the whole text, (2) scan it, (3) mask, (4) only then cut it to the kept size, (5) only then store or frame it.** Nothing unscanned is ever written to `turn_steps`, `step-details.db` or a frame; labels and `error` are built from the masked text.
- **Args are scanned at `item.started`**, before the first row or frame is written, because the label object and the grey hint come from them. Output is scanned at step end.
- **Whole-text scan.** The full args and the full output (buffered in memory up to 1 MiB each) go through the pipeline that exists: JSON keys matching `isSecretName` (server/redact.ts) → `•••`; then the composite text scan `scanTurnText` (the checker behind `checkTurnUnit`, redact-stream-release.ts) with the `bot-package-scan` rules (provider tokens, bearer, JWT, private keys, cookies), `basic-auth-mask` and `financial-ids`. **`NAME=value` and `Authorization:` masking applies to output text as well as the command line**, and URL query params named token/key/sig/code are masked. The head/tail cut runs on the masked result, so a key whose BEGIN line would fall in the dropped middle is already masked as a whole.
- **Fail closed.** Text the scan cannot finish is withheld whole: "Not shown: too large to check for secrets (3.2 MB)". The label, status and sizes stay. `SECRET_SCAN_BUDGET` counts scan work, not bytes, so the real ceiling is below 1 MiB. The builder measures it and writes it in DONE, and a witness asserts that a plain 64 KB log (twice the kept size) is shown. If that witness cannot pass, it is a FABLE-DESIGN question, never a silent ship.
- **Live tail.** Deltas feed one scanner per running step, in arrival order from the first byte, whether or not anyone is watching. It is the release machine the reply text already uses, `createTurnTextPolicy` (server/redact-turn.ts:42): it holds each line until it is complete, passes it through the full composite check (`checkTurnUnit`, the same rules as the whole-text scan, so bare tokens such as `ghp_…` are caught, not only `NAME=value` labels), and releases only what passed. The label detector alone (`scanLabelDelta`) is not enough and is never used by itself. If the policy latches (a hit it cannot bound, or its budget), the tail stops: "Live output hidden; it shows when the step finishes, if safe." The 24 KB tail ring is filled with **released** text only, so neither a frame boundary nor ring eviction can split a secret. Never a per-frame regex. At step end the whole-text scan result replaces the tail.
- **Masked turns.** When the turn's audience mask is on (`bus.audienceMaskedFor(event)`, read once at index.ts:13270 and applied to tool rows at 13498/13541 today; it defaults to masked for an unknown event), the step is stored and framed **verb only**: no object, no error text, no detail (`withheld:"masked-turn"`). This is applied on the server where the row and frame are built; a client is never trusted to hide anything.
- **Who can see steps.** Only the desktop and the proven owner's phone (route class `companion`, §5). At dev/1022 there is no other human viewer of a transcript: `guest` and `other-human` are message senders (index.ts:2552), not viewers. Step frames and details are never sent to outbound channels (WhatsApp, Telegram, webhooks) or to other bots. Any future non-owner connection gets the verb-only projection from the same server projector, by default.
- **Witnesses:** a private key placed across the 8 KB cut and across the tail cut → masked whole; a bare provider token in one delta, and one split across two deltas → never in any frame; a 2 MiB output → withheld; a local door or MCP caller gets no step route and no step frame; a masked turn's frame and row have no `object`; `NAME=value` in output → masked. "Copy" copies the masked text.

## 9. Performance at scale (murage-design-for-extreme-scale)
- **Server:** every step costs a fixed number of indexed writes and one small frame, whatever the turn length; no history scan, no array copy (today `extendStepLine` copies up to 200 strings and rescans `rowsAfter` per step). Eviction and the 5,000-row ring are O(1) amortised. Boot sweep is one pass over distinct thread ids.
- **Client:** a collapsed group renders its header only (0 row nodes). An open group loads rows in pages of 200 and virtualises above 100 rows (about 40 nodes). A detail is fetched and rendered only while open. A transcript page holds one small message per group, never step arrays.
- **Witnesses:** a 600-step fixture turn asserts (a) writes per step are constant (count the statements and frames at step 10 and step 600: equal), (b) every frame ≤ 512 B, (c) an open group renders ≤ 60 row nodes, (d) an upsert re-renders only its row and the header, (e) 20 bots × 600 steps keep `step-details.db` at or under the cap.
