## PURPOSE
A routine that runs right after Murage restarts (or at any time its turn is refused at a late write and rebuilt) gives the owner its one reply. Its run reads as what really happened, and the owner hears about it once.

## USER PROMISES
- P1. When a routine's turn is refused at a late write and Murage rebuilds it, the run stays one run. The rebuilt reply completes it: one reply, run Completed, one "done" ring, no "routine failed" ring and no turn-failed buzz. This holds for the turn that resumes a run after its card is answered too.
- P2. Every routine run ends exactly once: completed, failed or cancelled. That end gives exactly one ring: "done" for completed, "routine failed" for failed, nothing for an owner cancel. A redelivered event, a stale callback, a failed save or a restart never adds a second end or loses the ring. A ring re-sent after a crash carries the run's stable delivery identity, so the phone push is deduplicated durably and the desktop notification replaces the earlier one (K2). Stated residue (section 9 Parked): a run whose end was never saved (its save failed and the process died before the in-process recovery saved it) is, after restart, an unfinished run and is told once more as "Murage restarted…".
- P3. A routine never sends its prompt twice by itself. Once a run has started (its first provider write, or a card resume) it is never queued again at restart or on a busy database. The one exception is shipped behaviour kept as is (1.0.4 SL-I I3): if the engine refuses the run's first turn with its plan limit before any model activity (no tool, reasoning or reply; the engine's own refusal text does not count), the run waits for the reset and runs once, at most LIMIT_WAIT_TRIES times. A resumed run (after a card) never waits on the limit: it ends failed with the limit line. A run that provably never wrote anything may be queued again and then runs once.
- P4. A reply only counts for the run whose own accepted turn produced it. A late event of an earlier turn (pre-restart, stopped, refused, or the turn that ended before the card was answered) never completes or fails a different run, or the same run's later turn.
- P5. When the rebuilds run out, or no rebuild can start, or the engine never confirms the refused turn closed, the run ends failed once, never silent, with the line the owner sees in the conversation. An owner Stop (conversation Stop or the routine's Cancel) while a rebuild is owed ends the run cancelled, and no rebuild writes after it. The refusal row follows the JOINT RULING STOP-VS-REFUSAL at the refusal's real freeze: the OWNER's Stop with its close receipt confirmed -> no row; an owner Stop held, rejected or with nothing to close, or any host stop (run limit, engine change) -> the row shows, durably. No turn ever ends with neither.
- P6 (MAIN-RULING 02:31Z, int-1020q-late-n4/QUESTIONS-FOR-MAIN.md:264, verbatim: "refuse-if-no-task extended to owner routines + card continuations"; built in 99933a519c, index.ts:18984-18991, the check `assertHandoffRecoveryCarriesTask` at :18991). A scheduled/manual/webhook/channel run's prompt is a stored thread row (startTurn appends it, index.ts:17131-17141), so its last-resort rebuild carries that stored line, named and fenced again, and completes by P1. A card continuation's note is synthetic (`card-…`, never stored, index.ts:17130), so its last-resort rebuild is refused with its card and the run ends FAILED. No run ever reads "ran" having sent only the static recovery line.

## 0. Why rev 2 failed, and the redesign
Rev 2 kept the base's shape: index.ts calls `routines.settleDispatch(token, line)` at each exit it knows, and two places ring (the fold for "done", failRun for "failed"). Review findings cluster on exactly those two choices:
- **Exits enumerated one by one** (Astra 2, 3, 4, 7, 8, 13): each round found an exit with no settlement or the wrong line: the sealed lease's unbounded teardown, a Stop after `take("rebuild")`, a quiet setup cancel of the rebuild, the released/uncertain row, the sealed path never unbinding T, host retire/reconnect still thread-keyed, the setup/refusal retry spreading `seatWaitRunId`.
- **Rings split between fold and manager** (Astra 1, 11, 12, 6; Fable 2a/2b): a released direct slot drops the acceptance so a buffered reply never replays; the capped `callRunByTurn` loses origin; a failed save loses the completion ring; crash windows lose or repeat a ring.
- **Requeue and resume not phase-aware** (Fable new-1, Astra 9, 10): a resumed run requeues on busy/limit and re-sends its prompt; a failed resume commit strands the run.

Rev 3 replaces the enumeration with three owned objects, each with ONE terminal path and a backstop:
1. **The run outcome (manager).** One commit function ends a run, sets a persisted `ringOwed`, and rings from that commit. One persisted predicate `started(run)` decides every requeue (section 3, K1-K3).
2. **The dispatch handle (manager-issued, carried by the turn).** `RoutineDispatch` replaces the bare `{runId, seq}` token in opts. It is the only routine API index.ts may call. It lives on the direct generation record (not a capped map) and on the ledger lease (section 3, H1-H5).
3. **The refusal obligation (index.ts).** One `RefusalObligation` per refused provider turn chain carries the JOINT RULING row decision and the run's outcome for that refusal. It survives `take("rebuild")`, rides into the rebuild's opts, and is discharged exactly once: handover (the rebuild's first provider write), freeze (row or confirmed-Stop receipt + run outcome), or unconfirmed close. Its backstop is the one choke point every direct turn passes, `directRuns.release` (section 3, R1-R6).

Rev 2 items kept (re-expressed on these objects): binding through acceptance for every in-scope run kind (G1), the card resume's own seq (G4), the token-closed fence (G3), refusal-owed for every ticket kind (G6), and never-a-first-seat-wait for rebuilds (G7).

## 3. The state machine and its three objects
Scope: runs with target "bot" that dispatch a direct turn (schedule, manual, webhook, channel) and the card resume of a schedule/manual run. Out of scope, unchanged: room-goal runs (including project delivery, COMPLETED at delivery, routines.ts:3700-3714), finishGoalRun (:4132), file-watch (:4554-4565).

```
persisted: QUEUED ──dispatch(seq=++n)──▶ RUNNING ──▶ COMPLETED | FAILED | CANCELLED   (absorbing; ringOwed set in the same commit)
           RUNNING = running | waiting | needs-you.  started(run) := seatGrantedAt !== undefined || resumedAt !== undefined  (persisted)
in memory while RUNNING (one live RoutineDispatch per run; a new seq replaces it and closes the old one):
  D0 DISPATCHING(h)       handle issued; handback window open: pre-acceptance events are candidates
  D1 BOUND(h, T)          h.accepted(T): only T's events apply
  D2 OWED(h, O)           T refused late with refusalOwed: O = RefusalObligation; T retired + R unbound at O's creation (both routes)
  D3 REBUILDING(h, O)     O rides into the rebuild's startTurn (same h) -> D0 -> handover at T' first write -> D1(T')
  D4 NEEDS_YOU(h, T ended) T ended ok with a harness card open
  D4 --owner answers card--------------▶ D0(h' = new seq)     one commit (K4); h closed
  D4 --card closed by a host exit------▶ FAILED (host line)   never resumes (H5)
out of RUNNING, only through K1 (outcome commit):
  D1 T terminal ok -> COMPLETED; T terminal failed -> FAILED (never requeued once started, K3), except the K3 limit rule: a first-turn plan-limit refusal before any activity -> QUEUED(limitWait)
  D2/D3 O.freeze -> FAILED with the visible row's line | CANCELLED (owner, confirmed receipt) | FAILED host-stopped
  D2/D3 O.unconfirmedClose -> FAILED unconfirmed-stop line (thread stays retained)
  any  run limit | owner cancel -> FAILED(limit) | CANCELLED; h closes, O (if any) freezes by the JOINT RULING
  D0   h.end(...) from an admission/setup failure -> FAILED, or QUEUED only when !started(run), or by the K3 limit rule (K3)
restart (the only cross-process transition, routines.ts:1999-2061): RUNNING with a well-formed seatWait and !started -> QUEUED (or
  CANCELLED if a later occurrence is queued); every other RUNNING -> FAILED "Murage restarted while this routine was running" via K1.
  Terminal rows with ringOwed -> ring once (K2). Handles, obligations, candidates, registry die with the process; nothing is re-armed.
```

### K. The run outcome (routines.ts)
- **K1. One outcome commit.** `endRun(run, outcome)` is the only code that sets a terminal status: it absorbs `failRun`, the `completed` branch of `applyRunEvent` (routines.ts:4238-4249), cancel, and the boot pass's fail. It acts on the LIVE record from `lookupRun`. Provider and dispatch outcomes (completed, failed) no-op unless the run is live; an explicit owner cancel keeps today's guard `isOpen` (cancelRun, routines.ts:3107-3108), so a run still QUEUED behind a seat or spend hold is cancelled and never dispatched (Astra r3-1 new 2). It closes the live handle (H1), sets status/error/finishedAt and `ringOwed = outcome` (except owner cancel) in ONE `save`. Then, whether that save succeeded or threw (a throw is caught, counted in saveFaults and left to the existing recovery, :4934-5004), it rings (K2). It never throws to its caller. A failed owner-cancel save leaves the run CANCELLED in memory (no restore, unlike commitScoped's rethrow at :3112), so this process never runs it again. If the process dies before recovery saves it, the run reloads live and the boot pass fails it once with "Murage restarted…" (the P2 unsaved-end residue, Parked) (Fable R3 #4).
- **K2. The ring comes from the commit, once.** `ringOwed` is a small persisted object, not a flag: `{ kind: "done" | "routine-failed", threadId (routineReportThread or run.threadId), detail (redacted, ≤500 chars: reply/output/routineName, or run.error) }`, written in the outcome commit. Right after the commit, `endRun` calls `onRunCompleted` (new; with the live turn's duration and files receipt when this process has them, index.ts:14194-14210; dev/1022 also skips this frame for a `commandRefusal` turn, see r5 note A5) or `onRunFailed`, then clears `ringOwed` in memory and saves. Every routine outcome ring carries a stable delivery identity `routine-run:<runId>` (one end per run): as the notification's `deliveryId` (today a random UUID for "done", index.ts:14207) and as a new optional `collapseId` that the push outbox uses for its collapse key and its durable duplicate check, the same pattern it already uses for connector-reconnect (`store.latestForRequest`, mobile-push-outbox.ts:136, :142). On the desktop, the existing DURABLE receipt path that connector-reconnect already uses (electron/attention-main.mjs:339-352: `connectorReceipts.attempt(home, deliveryId)` before showing, `delivered(...)` on show) is generalised to `durableReceipts` and applied to both routine outcome kinds ("done" and "routine-failed") whose deliveryId is `routine-run:…`; the router's receipt key for those frames is `home|deliveryId` with no epoch (electron/attention-router.mjs:50, :367-378 today key by epoch and skip routine-failed), so a server restart, a reconnect or a dismissed first notice cannot make it show again. A ring re-sent from `ringOwed` after a crash (between broadcast and the clear save) is therefore never a second push and never a second desktop notice (Astra 6). A recovered ring has no duration/files receipt (stated; asserted at W5 C3/C4). Because the in-memory record already has `ringOwed` cleared, a later recovery save persists it cleared (Astra 12: a failed first save still rings once and recovery cannot re-ring). A ring re-sent from a saved `ringOwed` (the boot pass) is the OWNER's ring only: `onRunFailed(run, { recovered: true })` skips `reportTeamIncident` (index.ts:20467), so a peer never gets the incident twice. The cost is that if the crash came before the first ring, no peer report is sent; this fails toward silence to a peer and never to the owner (Fable R3 #3; asserted at W5 C3/C4). The boot pass rings once for every terminal row still carrying `ringOwed` (a crash after the commit and before the ring, Astra 6) and for every run it fails itself (its own commit sets `ringOwed` first). The fold never rings "done" for a routine-origin turn (H3). `onRunNeedsYou` is unchanged and is the only notice at T1's end (Fable 2b: the base's extra "done" at needs-you is removed; W13 asserts it).
- **K3. Two requeue rules (rev 4).** `started(run)` is persisted. `seatGrantedAt` is stamped at the run's first provider submission by `h.submitted()` (H2), not only after a recorded wait (today routines.ts:4590-4599 stamps only when a wait existed, Astra 7). `resumedAt` is set by the resume commit (K4).
  - **Busy and boot:** `requeueBusy` (routines.ts:3375-3380) and the boot requeue (routines.ts:2005-2020) check `!started(run)` first. A started run that reaches one of them ends FAILED via K1 with "Murage's database was busy and this run could not continue. Run the routine again." (busy) or the boot line (Fable new-1, Astra 9).
  - **Plan limit (both sites, routines.ts:4206 failed terminal and routines.ts:4272 settle):** `limitWaitFor` queues the run only when ALL hold: (1) `run.resumedAt === undefined`; (2) the shipped I3 test still accepts the refusal, judged on the EXACT turn's limit record. For a terminal that is `limitRefusalOfTurn` (index.ts:16083-16098), which already returns null once `turn.activity` is set (limit-continuation.ts:135-136: content delta, a tool or reasoning item, an image) and accepts assistant text only when that text is itself the refusal (`relayedRefusalText`, limit-continuation.ts:77-80). For the settle site it is the plan-limit dispatch message (index.ts:16124). (3) The live handle saw no model output for this dispatch. The manager keeps two flags on h, set from every candidate (pre-acceptance, buffered) or bound event of h with the same event tests as limit-continuation.ts:129-136: `h.activitySeen` (what sets `turn.activity`) and `h.textSeen` (what sets `turn.textActivity`). The terminal site requires `!h.activitySeen` (text is judged by I1's refusal-text rule). The settle site has no terminal and no refusal-text check, so it requires `!h.activitySeen && !h.textSeen`: a dispatch that wrote any assistant text and then rejected with the plan-limit message ends FAILED and is never re-sent (Astra r4-1 #2).

Otherwise a run that reaches either site ends FAILED via K1 with the existing limit fail line (`routineLimitFailedLine`). When it does queue, the same save that sets QUEUED and `limitWait` also clears `seatGrantedAt` (alongside the `startedAt` it clears today, routines.ts:4397). This is the one sanctioned requeue of a submitted run: the engine refused it before any work, so the next dispatch re-stamps it on its own submission. LIMIT_WAIT_TRIES (routines.ts:4393) still bounds it to the third refusal. This keeps 1.0.4 SL-I I3 for every first-turn limit refusal, including the channel's "waiting on the limit" notice (index.ts:16143-16145) (Fable R3 #1).

For `answered`/`closed-unanswered` with `turnEnded` it builds the new state on a copy (cardsOpen, turnEnded cleared, resumedAt, status running) and commits it; ONLY after the commit returns does it issue `seq' = ++dispatchSeq`, create the new handle h' (fresh candidates, replay, lostTurns; old replay timer cleared), close h, clear the bound turn, and return `{ resume: true, handle: h' }`. ### H. The dispatch handle (routines.ts issues it; index.ts carries it)
`RoutineDispatch` = `{ runId, seq }` plus methods bound to the manager. ### Fences
- F1 dispatch: the handle (runId, seq); a new seq for every dispatch and every card resume.
- F2 turn: only `h.accepted(T)` binds; a refused T is retired manager-wide at O's creation (registry 4,096).
- F3 epoch: handles, obligations, candidates, registry are in memory only (the one exception is R7's row debt, which re-arms nothing); the boot pass is the only cross-process transition; a handle is never persisted (the held continuation stores the run id, H).
- F4 ring: K2 (from the commit, `ringOwed`), H3 (fold by exact origin).
- F5 token-closed: H1; after K1, a new seq, the limit or cancel, nothing writes for h, and O decides only by R4.
- F6 content: P6.

## 4. The one terminal path
A run leaves RUNNING only in K1. K1 is reached only from `applyRunEvent` for the bound turn of the live run, a handle method (H1-H5), an obligation discharge (R3-R6) through its handle, the run limit, cancel, or the boot pass. A terminal run is absorbing: every later event, handle call, obligation discharge, card answer or boot pass leaves it unchanged and rings nothing. The refusal card's `turn-failed` buzz stays muted for automation and card continuations (`turnFailureBuzzes`, notify.ts:73).

## 5. Fail-closed defaults
- refusalOwed unknown, throwing or unwired: not owed; R fails at T's terminal (visible).
- A routine turn with no handle: not started; K1 FAILED with the run-kind lost-track line. Channel keeps "Murage lost track of this reply; send the message again"; every other kind: "Murage lost track of this run's reply. Run the routine again to get it." Same split at the provenance-lost settle (routines.ts:4080).
- An obligation whose chain ends on a path nobody named: R5 freezes it (row shown unless a receipt).
- Acceptance that never arrives: the dispatch error/catch path ends R through h; with no run limit and an engine that never returns, R stays visibly running until Stop or restart (base behaviour, unchanged; the held no-tools continuation likewise, Parked).
- Saves that throw: K1 still rings once (K2); H2 refuses the write; K4 fails the run visibly. None throws into acceptance, the fold or the card answer.
- Restart in any D-state: FAILED once via the boot pass, never re-sent (P3).
- A reply that lands after R is terminal stays visible in the thread, rings nothing and does not change R.
