## F45: a Cloud turn killed by its memory cap says why and retries once (upstream 405846c9b)

Today: a turn runs in its own scope `murage-turn-<16hex>.scope` under `murage-turns.slice` (MemoryMax=40% per scope, 50% for the slice,
deploy/cloud-home/murage-turn-launch.py:53, murage-turns.slice). When the kernel OOM-kills it, the server sees a plain SIGKILL and the
person gets the generic engine error. Nothing names memory, nothing retries.

Detection (server only, no launcher change):
- cgroup v2 `memory.events` is hierarchical (no `memory_localevents` on a home), so `/sys/fs/cgroup/murage.slice/murage-turns.slice/memory.events`
  `oom_kill` counts every OOM kill in any turn scope. The scope dir is world-readable already (cloud-process-hooks.ts:5).
- procs.ts reads the slice's `oom_kill` when it starts a Cloud turn (next to `registerCloudTurnUnit`, procs.ts:479) and again at the
  child's `close`. A turn is "stopped for memory" only when ALL hold: MURAGE_CLOUD_ROLE=home, the child ended by SIGKILL, it was not our
  own stop (`killed`/stop route not set), and the counter rose. Unreadable file = not memory (fail closed to today's behaviour).
- Upstream's wider system (oom_score_adj for browsers, the day's pressure ledger, the room card and plan upsell) is NOT in this item.
  Skip reason: it needs the Admin offer API and new UI (L-COPY, 8 locales); F45's row is only "says why and retries once".

Wording (one line, replaces the generic error; L-COPY id `cloud.turn.memoryStopped`):
"Your Cloud ran out of memory, so I stopped this task to keep everything else running." and, when it retries, "Trying it once more."

Retry once, guarded (this is the state and data part GrokBuild rules on):
- Auto-retry only when the killed turn made NO side-effecting step: no tool call reached execution (no approval granted, no MCP/tool
  result recorded for the turn). A turn that already acted (sent a message, wrote a file, spent money) is never re-run by itself: it ends with
  the line and the normal Try again, because a re-run could repeat the action.
- At most one retry per turn id, recorded on the turn (`memoryRetry: true`), so a restart never retries again. The retry is the same
  request (same thread, same message), started after the scope is gone; if the retry is also stopped for memory it ends with the line only.
- Never for a routine/Chief run that has its own retry policy; never while the person pressed Stop.
- Tests (fail on base): fake slice file + SIGKILL -> memory line and exactly one retry; counter unchanged -> generic error, no retry;
  tool already executed -> line, no retry; retry killed again -> line, no second retry; unreadable file -> today's behaviour.

## F35: better-auth 1.7.1 -> 1.7.7 (upstream 095804cb8)

Facts: cloudflare/control-plane/package.json:7 pins "1.7.1". Advisory GHSA-965c-763c-88jm (OAuth state accepted as a Magic Link token) does
not reach us today: auth.ts plugins are emailOTP only, no magicLink, no social OAuth. This is an upgrade to stay current, not a live fix.
Change:
1. Pin "better-auth": "1.7.7"; regenerate the control-plane lockfile on the build host against registry.npmjs.org (not on the Mac).
2. `database: { generateId: "uuid", validateSchema: false }`: 1.7.3+ introspects D1 on every auth instance (ours is per request), one
   more D1 round trip per request; our pinned migrations own the schema.
3. New migration `0111_account_drop_issuer.sql`: `DROP INDEX IF EXISTS "account_issuer_accountId_uidx"; ALTER TABLE "account" DROP COLUMN "issuer";`
   1.7.3+ never writes `issuer`, so the NOT NULL column from 0001 would refuse every new account row.
Deploy order (MurageCloud runs it; this lane never touches production or murage-staging.token): the old Worker writes `issuer`, the new one
cannot. Migration and Worker go out in one step (migrate, then deploy at once); the gap only affects creating a NEW `account` row. Ask for
GrokBuild: confirm whether emailOTP sign-up writes an `account` row at all (if not, the gap affects nothing we use).
Tests: an account row inserts on the migrated schema (fails on base: NOT NULL issuer); existing auth/OTP tests green on 1.7.7; the
per-request auth instance makes no schema-introspection query.

## B99 re-scoped: honest capacity at the tunnel cap, guarded reclaim (upstream bfed2e16b, b2d64f39b)

Facts: our endpoints.ts has no capacity model: no tunnel count, no 429-at-cap mapping, no idle or stalled-provisioning reclaim
(endpoints.ts:213 is our own D1 rate limit; :1162 cleanup handles forbidden machine states only). Upstream's two commits sit on a
multi-account Cloudflare pool (CLOUDFLARE_ENDPOINT_ACCOUNTS, migration 0007, tunnel-capacity.ts).
Re-scope (port the behaviour, not the pool):
- KEEP: a tunnel-creation 429 from Cloudflare while the account is at or over its tunnel limit is capacity: 503 `endpoint_capacity`,
  Retry-After 600, and a ten-minute gate so apps stop retrying; any other 429 stays rate limited. A 90% alert (redacted) when the count
  crosses 90% of the limit.
- KEEP: reclaim of tunnels left by provisioning requests that stopped (lease expired, row untouched for the quiet period, never handed out
  an address), each re-verified by tunnel ID AND name before delete. Never a ready endpoint.
- SKIP: second Cloudflare account and DNS-quota account moves. Checked reason: one account today, far below 1,000 tunnels; a second account
  is a production config change for MurageCloud, not code we can prove here.
Tests: 429 at cap -> 503 + Retry-After + gate; 429 below cap -> rate limited, no gate; stalled-provisioning tunnel reclaimed only on ID+name
match; ready endpoint never reclaimed.
