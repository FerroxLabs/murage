# AB-ENGINE-PATCH-1019: authenticating the agent-browser engine listeners

Status: sizing only (PKT0-19, 2026-11-09). Source read: vercel-labs/agent-browser v0.36.0 (exact tag, cloned on build-host under build-host:/fuigo-builds/pkt0/ab-src).

## What Murage owns and what it does not

`server/browser-native-relay.ts` (:389-420, `connect`) is a WebSocket CLIENT. It dials `ws://127.0.0.1:<port>/?pacing=ack&maxFps=10`, where the port comes from the engine's `stream status`. Murage opens no listener there, so Murage cannot check a token on that handshake: there is nothing on Murage's side to check it. A token has to be enforced by the engine's stream server, and the relay can only present it. Sending a token to the stock 0.36.0 binary does nothing, so no token code was added to the relay in PKT0-19 (it would be theater).

Every unauthenticated listener is inside the engine:

| Listener | Engine code | Today |
|---|---|---|
| Stream + input WebSocket | `cli/src/native/stream/mod.rs` `start_inner` (bind 127.0.0.1), `stream/websocket.rs:281-319` `handle_ws_client` (only an Origin check, `is_allowed_origin`) | any local client receives frames and can inject input |
| Daemon command channel, Windows | `cli/src/native/daemon.rs:369-380` TCP 127.0.0.1, port in `<session>.port`; client `connection.rs:414,1007` | JSON-line actions, no credential |
| Daemon channel, Unix | `daemon.rs:234` Unix socket in Murage's 0700 dir | same-user only, fine |
| Chromium CDP | `cli/src/native/cdp/chrome.rs:461` `--remote-debugging-port=0` | `/json/version` reveals the browser WS path to any local client |

## Sizing

1. Stream token (small, ~1 day incl. tests). In `handle_ws_client`'s header callback, read `AGENT_BROWSER_CONTROL_TOKEN` from the engine env and require it in `Sec-WebSocket-Protocol` (or `?token=`), compared in constant time; absent or wrong gives 401 before any frame or input. Missing env gives refuse (fail closed). Murage side: generate 32 random bytes per launch, put it in `spec.env` only, present it in `connect()`. Unit test in `websocket.rs` tests (accept_async pattern at :829) plus a TS test against a fake server that a tokenless client is refused.
2. Daemon TCP token, Windows (small, ~1 day). Require a `token` on the first line of each connection in `daemon.rs handle_connection`; the engine CLI client (`connection.rs`) and Murage's direct close in `browser-native-relay.ts` (`close()`, win32 branch) add it. The CLI inherits the env, so both sides agree.
3. CDP off the port (large, 1-2 weeks). `--remote-debugging-pipe` needs a pipe transport in `cdp/client.rs` (525 lines, WebSocket-only today) and a fd-3/4 launch in `chrome.rs`. Murage's own guards (`BrowserDocumentGuard`, `startTargetGuard`, before-unload guard) open a SECOND CDP connection from `get cdp-url`; a pipe allows one client, so those must move inside the engine as fixed authenticated operations, then be re-proven (this includes the OOPIF lock added in PKT0-19, which uses that connection). Fallback if the pipe cannot ship everywhere: no token option exists for Chromium's port mode, so the port stays reachable; say so.
4. Windows named pipes with a current-user-SID DACL (large, 1 week plus a real Windows machine): replace the TCP daemon and stream listeners via the existing vendor path (`third_party/browser/README.md:11-24`, `scripts/build-windows-browser-vendor.mjs`). A unit test with a fake peer SID is possible; the real proof (a pipe opened by another SID is refused) needs Windows.
5. Release: today mac and linux ship the OFFICIAL Vercel executables; only Windows is an `omb` vendor build. Any of 1-4 makes all three platforms vendor builds (pin, sign, provenance, native cold-start and close/reopen checks on each OS). That is the decision for Sean.

## Threat boundary to write in the code once built

Kept out: other OS accounts and any loopback client without the per-launch token. Out of scope: same-account processes with debug rights (they can read the token from the process environment).

## Recommended order

1 and 2 first (cheap, real for the stream and Windows daemon), then 3 and 4. Until 3 ships, the raw CDP port remains reachable by other local users, so Pop out view must not claim other-user isolation.

### Design

1. Token source. Murage generates 32 random bytes per `agentBrowserIntegration` call (per launch of a bot's browser session), hex, and puts it ONLY in the child env as `AGENT_BROWSER_CONTROL_TOKEN` (local and Cloud-home branches). Env is not argv. The CLI spawns the daemon with its own env, so CLI, daemon and stream server agree with no second channel.
2. `native/control_token.rs`: `configured() -> Option<[u8;32]>` (env, exactly 64 hex chars, else None). Comparison uses `subtle::ConstantTimeEq` over the SHA-256 digests of both sides (`subtle`, `hmac` and `sha2` are already in Cargo.lock; they become direct deps). No hand-written XOR fold. FAIL CLOSED: the guarded listeners never start, and the Windows daemon never binds or writes its `.port` file, when the env is missing or malformed; the error goes to stderr and the command that started it, before readiness is advertised.
3. Stream server (every platform). `handle_connection` reads the request head with a bounded loop: `peek` into an 8192-byte buffer, return once `\r\n\r\n` is inside it, otherwise `sleep(10 ms)` and peek again (peek consumes nothing, so the sleep is what prevents a spin; no bytes are consumed, so tungstenite and `handle_http_request` still see the whole request unchanged). The whole loop sits inside `tokio::time::timeout(5 s)`, independent of the loop body; a head that does not complete, or exceeds 8192 bytes, is refused with 400 and never partially trusted. WebSocket: the `accept_hdr_async` callback in `handle_ws_client` checks `Authorization: Bearer <token>` on the parsed handshake, 401 before any frame is queued or input read. HTTP (all methods except `OPTIONS`, which returns nothing and invokes no handler): same header, else 401; `/api/command` keeps its same-origin check. No `?token=` (URLs reach logs). Authorization is read from headers only. The engine's embedded browser dashboard cannot set headers and stops working under Murage's launch; Murage does not use it.
4. Windows daemon TCP uses mutual challenge-response, so the token is never sent to whoever holds the port (a local user can squat the hash-derived or fallback loopback port, and `connection.rs` connects by port). First line from the client: `{"hello":"<32 random hex>"}`. Server replies `{"proof":"<HMAC-SHA256(token, "srv"||cn)>","nonce":"<32 random hex>"}`. The client verifies `proof` in constant time BEFORE sending anything else, then sends `{"auth":"<HMAC-SHA256(token, "cli"||sn||cn)>"}`; the server checks it in constant time. A squatter could still RELAY that handshake to the real daemon, so authentication does not stop at the handshake: both sides derive a session key `K = HMAC-SHA256(token, "key"||cn||sn)` and every later line in either direction is framed `{"n":<counter>,"m":<the original message as a string>,"mac":"<HMAC-SHA256(K, dir||n||m)>"}` with `dir` = `c` or `s`, strictly increasing counters per direction; a bad MAC, a repeated or skipped counter, or an unframed line closes the connection. A relaying squatter can therefore neither inject nor alter a command or a reply (it can only drop or read traffic; message confidentiality is not claimed). The same framing makes a forged `stream status` reply (the stream port) impossible on Windows. Only after authentication are command lines read; `idle_activity.mark()` and `execute_command` are reachable only after it, and no command JSON ever carries credential material (nothing to strip, nothing to broadcast). The Unix socket path keeps no token (same-user by directory permission) but with a token env present the daemon refuses to bind unless the socket directory is owned by the effective uid and has no group/other bits (mode & 0o077 == 0), and the socket file is chmod 0600. Clients: `connection.rs`, `stream/http.rs` forwarding and `dashboard.rs` use one shared client helper; Murage's direct win32 close in `browser-native-relay.ts` does the same handshake with node `crypto.createHmac`.
5. Murage side. `browser-engine.ts` adds the env var. `browser-native-relay.ts connect()` passes `headers: { Authorization: "Bearer <token>" }` to `new WebSocket` (the Cloud relay path only swaps `createConnection`). Stale daemon: a daemon left running by an earlier Murage launch holds an older token. On Unix the engine does not check the token on its socket, so the visible symptom is a 401 at the stream handshake. On Windows the CLI's handshake fails during any engine command (readiness, attach, `stream status`), and the engine reports it with a distinct code: `{"success":false,"error":"Unauthorized","code":"control_token_mismatch"}`. Murage's one recovery covers both entry points: the stop-and-forget half of `close()` in `browser-native-relay.ts` (the block that probes the session's own socket, then stops the pid-file daemon with the identity checks in `windowsDaemonStopDecision` on Windows and the SIGTERM/SIGKILL path on Unix) is lifted unchanged into `stopStaleDaemon()`; the engine-command wrapper (`command()`) and `connect()` call it ONCE per browser session on `control_token_mismatch` or on the 401 handshake, then repeat the failed step once; a second failure surfaces as the existing "Browser stream unavailable" / engine error. The refactor is covered by the existing close tests, which must stay green and unchanged. No new kill logic.
6. Tests. Rust: `control_token` unit tests (right, wrong, same-length wrong, truncated, empty, absent, env missing refuses, env malformed refuses); `websocket.rs` tests at the existing accept_hdr_async pattern (tokenless 401, wrong 401, right accepted and a frame flows); `http.rs` tests (tokenless GET `/api/status` and POST `/api/command` 401, right token served, OPTIONS answers, fragmented head across two writes still accepted, oversized head refused); daemon `handle_connection` over `tokio::io::duplex` (no hello, bad auth, wrong proof from a fake server is refused by the client helper before it sends anything, right sequence runs and the command executes, wrong token never reaches `execute_command`); Unix directory-mode refusal test; a relay test (a middle man that forwards the handshake then injects a framed or unframed line, or replays/skips a counter, is cut off); `dashboard start` and the `inspect` action refuse when a token is configured; stream/Windows bind refuse with the env missing or malformed before any port file exists. TS (vitest): relay test against a fake `ws` server that refuses a handshake without the Authorization header and accepts the right one; the 401 recovery runs once and only once; `agentBrowserIntegration` gives a fresh 64-hex token per call, in env and never in argv; win32 close performs the handshake against a fake daemon that checks the HMACs (platform stubbed).
7. Build and delivery. `cargo build --release` for x86_64-unknown-linux-gnu on build-host, ONE cargo build at a time in build-host:/fuigo-builds/abpatch/, target dir deleted after. Mac and Windows binaries are written down, not built here (no Mac builds; Windows needs an `omb` vendor build): a "Release steps" section is added when the build is done.

### Threat boundary

Kept out: other OS accounts and any loopback client (including a web page that can reach 127.0.0.1) without the per-launch token; a process squatting the daemon port cannot learn the token. Out of scope, unchanged: same-account processes with debug rights, the raw Chromium CDP port (needs pipe mode, deferred by Sean's ruling), and the stream bearer token being presented to the stream port (its port comes from the authenticated `stream status` answer, so a squatter would have to beat the engine's own bind).

## Part 2 rev B: bounded framing and single deadline  [2026-11-10, after Astra review 2 BLOCK]

Why: Astra (acct4) blocked 1ccca49 twice on item 4 (the blocking client checks elapsed time between reads, but each read still gets a fresh 5 s timeout, so a drip overruns the deadline), found no regression test for item 2 (negative counter), and found NEW item 8 (High): `daemon.rs:570` reads an unbounded line before its MAC is checked, so a tokenless squatter that relays a real handshake can then stream bytes with no newline until the daemon runs out of memory; the CLI reply reader (`connection.rs:1145`) and the `/api/command` forward reader (`http.rs:458`) have the same flaw. Two failed reviews on one item means redesign, not patching. Rev B replaces design 4's post-handshake framing and every reader in the Windows/daemon path with one rule. Everything else in designs 1-7 stands.

### B1. The rule (applies to every reader and writer on a daemon connection)

1. One absolute deadline per phase, computed ONCE, never refreshed by progress:
   - Handshake deadline `D_hs = now + 5 s`. Daemon: constructed IN THE ACCEPT LOOP the moment `accept()` returns, and passed through `tokio::spawn` into `handle_connection(.., hs_deadline)` and on into `server_handshake_by(.., hs_deadline)` (task scheduling delay counts against it). Client (CLI and `/api/command` forward): constructed the moment `connect` returns and passed into `client_handshake_blocking_by` / `client_handshake_async_by`. It covers every handshake read AND write. Production code calls only the `_by` variants with a deadline taken at those two points; the no-argument wrappers exist for tests and build `D_hs` on entry.
   - Client reply deadline `D_reply = now + read_timeout_for(cmd)` (the existing formula, `max(30 s, cmd.timeout + 10 s)`, moved into `control_token.rs` as `reply_budget(cmd)` so the CLI and the forwarder share it). Taken once, just before the command frame is written; it covers the command write and the whole reply read.
   - Daemon frame deadline `D_frame = now + 30 s`, taken each time the daemon starts waiting for a command frame (after the handshake, and after each reply is written); it covers the whole wait plus every byte of that frame. The daemon's reply write is bounded the same way (`now + 30 s` per reply). Every client in the inventory sends one command per connection immediately after `auth`, so no legitimate connection idles 30 s.
2. Each blocking operation uses the REMAINING time of its deadline. Blocking (CLI): before every `fill_buf`/`read` and every `write` call, `let left = deadline.remaining()?` (an error when zero or past, because `set_read_timeout(Some(ZERO))` is an error in std), then `set_read_timeout(Some(left))` / `set_write_timeout(Some(left))` on the socket. `WouldBlock` and `TimedOut` both map to `ReadError::TimedOut`; `Interrupted` retries (the deadline is rechecked). Writes go through `write_all_by(deadline)`, a loop of single `write` calls each preceded by the remaining-time timeout (std `write_all` would give every inner `write` the full timeout). Async (daemon, forwarder): every read and write is wrapped in `tokio::time::timeout_at(deadline, ..)`, which is absolute by construction. No code path may call `set_read_timeout` or `tokio::time::timeout` with a constant on a daemon connection after rev B; a grep for `timeout(HANDSHAKE` and `set_read_timeout(Some(Duration::from_secs` in the patched files is part of the review.
3. `Deadline` (in `control_token.rs`) wraps a `tokio::time::Instant` (tokio is built without `test-util`, so there is no paused clock; all timing tests run on real time with short injected budgets); `Deadline::after(budget)`, `remaining() -> Result<Duration, ReadError>`, `at() -> tokio::time::Instant`. Every bounded function takes a `Deadline` argument; `client_handshake_blocking`, `server_handshake`, `client_handshake_async` keep their 1ccca49 names as thin wrappers over the `_by(.., deadline)` variants (see 1).

### B2. One bounded line reader, length cap enforced before growth

- Pure core `LineAccumulator { buf: Vec<u8>, max: usize, grammar: Grammar }` with `feed(&mut self, available: &[u8]) -> Step` where `Step` is `NeedMore(consumed)`, `Done(consumed)` or `Reject(ReadError, consumed)`. It copies bytes up to and including the first `\n` and never lets `buf.len()` exceed `max` (the cap counts the whole line including the frame prefix and the `\n`); at `max` bytes with no `\n` it returns `Reject(TooLong)` and nothing more is read from that connection. `buf` grows only with bytes that actually arrived (no `with_capacity` from any peer-supplied number).
- Two thin wrappers share the core: `read_line_by(r: &mut impl AsyncBufRead, max, grammar, deadline)` (`timeout_at(deadline, r.fill_buf())`, feed, `consume`) and `read_line_by_blocking(r: &mut BufReader<S>, max, grammar, deadline) where S: Read + Timed`. `Timed` is a two-method trait (`set_read_timeout`, `set_write_timeout`) implemented for `connection::Connection`, `std::net::TcpStream`, and test fakes. The blocking client keeps ONE `BufReader` for the whole connection (handshake reply and framed reply), so the 1ccca49 byte-by-byte loop and its "BufReader would swallow bytes" problem both go away.
- `ReadError = TimedOut | TooLong | Closed | BadFrame | Io(kind)`. Each maps to a distinct, non-silent error string at the call site (`control_handshake_timeout`, `control_frame_too_large`, `control_token_mismatch` for BadFrame/MAC/counter, as today).
- Caps (constants in `control_token.rs`): `HANDSHAKE_LINE_MAX = 4096` (unchanged; hello/proof/auth lines), `COMMAND_PAYLOAD_MAX = 16 MiB` (client to daemon), `REPLY_PAYLOAD_MAX = 128 MiB` (daemon to client; covers screenshots and network bodies, which are base64 inside replies). A refused oversized reply is a visible error, never a truncated success.
- Every reader in scope uses it: daemon `handle_connection` (handshake lines, framed command lines, AND the plain Unix-socket command lines: cap `COMMAND_PAYLOAD_MAX`, no deadline, so Unix keeps upstream timing and gains only the cap); CLI `send_command_once` (handshake reply, framed reply, and the plain Unix reply with cap `REPLY_PAYLOAD_MAX` and `D_reply`); `/api/command` forwarder `relay_command_to_daemon` (same as the CLI, async). The stream server's head reader (design 3, peek loop inside one 5 s timeout, 8192-byte cap) already obeys the rule and is unchanged. Murage's `closeDaemonSession` obeys it in TS (B5).
- Windows-only call sites shrink to gate selection. The CLI body moves into `fn exchange<S: Read + Write + Timed>(stream, cmd, control: Option<&Token>, d_hs_budget, reply_budget) -> Result<Response, String>` and the forwarder body into `async fn relay_exchange<R, W>(..)`; both are compiled and tested on every platform, and the `#[cfg(windows)]` blocks only choose `Some(token)`. This puts the CLI and forwarder readers under Linux tests, which 1ccca49 could not do (its handshake/reply code is `cfg(windows)`).

### B3. Frame v2 (`ab1`): MAC checked before any parse

Post-handshake wire line, both directions, replacing the JSON `{"n","m","mac"}` frame:

`ab1 ` + `<n: exactly 16 lowercase hex digits>` + ` ` + `<mac: exactly 64 lowercase hex digits>` + ` ` + `<payload: UTF-8 bytes, no 0x0A>` + `\n`

- `mac = HMAC-SHA256(K, "ab1" || dir || n as 8 big-endian bytes || payload bytes)`, `dir` = `c` (client to daemon) or `s`. `K` and the handshake are unchanged from design 4.
- The fixed prefix is 86 bytes. With `Grammar::Framed`, the accumulator checks each of those 86 bytes AS IT ARRIVES (positions 0-3 `ab1 `, 4-19 `[0-9a-f]`, 20 space, 21-84 `[0-9a-f]`, 85 space) and rejects at the first wrong byte, before reading further. A legacy JSON frame is refused at byte 0, a negative counter (`-`) at byte 4.
- `Session::open(&mut self, line: &[u8]) -> Result<String, FrameError>`, in this order and no other: (1) prefix grammar recheck; (2) decode n and mac from the fixed hex fields into `[u8; 8]`/`[u8; 32]` with a strict lowercase-hex decoder (no serde, no `from_str_radix`, no sign handling); (3) compute the MAC over the raw payload bytes and compare in constant time (`Mac::verify_slice`); (4) `n == recv_n` exactly, then `recv_n = recv_n.checked_add(1)` (overflow closes); (5) only now `String::from_utf8(payload)`; the caller then `serde_json::from_str`s the message. Nothing touches JSON or UTF-8 before the MAC passes.
- `Session::seal(&mut self, payload: &str) -> Result<Vec<u8>, FrameError>` refuses a payload containing `\n` (serde_json never emits one, but it is enforced) and uses `checked_add` for its counter.
- Counter rule: u64 per direction per session, starting at 0, strictly +1, fixed-width lowercase hex. No sign, no exponent, no decimal point, no uppercase, no whitespace: a negative or non-integer counter is unrepresentable, and any frame whose `n` is not exactly the expected value (repeat, skip, `ffffffffffffffff`) closes the connection without advancing state. Nonce rule: `hello` and server nonces are exactly 32 LOWERCASE hex (tightened from `is_ascii_hexdigit`; TS drops its `/i`), fresh from `getrandom`/`randomBytes` per connection.
- Handshake lines (`hello`, `proof`, `auth`) stay JSON: they are pre-authentication by nature, capped at 4096 bytes, read under `D_hs`, and parsing them is what produces the authentication.

### B4. Tests (exact names; each red on 1ccca49, shown before the fix)

Red proof method: on a throwaway branch `red-revb` from 1ccca49, add ONLY the new tests plus a test-only shim, so all four tests COMPILE on 1ccca49 before any result counts. The shim declares, with no production behaviour change: the `Timed` trait (impl for the test fakes only), `Deadline`, the cap constants, `FrameError`, and two adapters on `Session`: `open_bytes(&mut self, &[u8]) -> Result<String, FrameError>` (on 1ccca49: `std::str::from_utf8` then the old `open`, `None` mapped to `FrameError::Bad`) and `seal_bytes(&mut self, &str) -> Vec<u8>` (old `seal` plus `\n`). On rev B the same two adapter names are thin pass-throughs to the new `open`/`seal`, so the tests are textually identical on both trees. A test counts as red only if it FAILS BY ASSERTION or by its own guard timeout, never by a compile error. Record `red.log`.

1. `native::control_token::tests::slow_peer_drip_fails_at_the_handshake_deadline` (item 4). Calls `client_handshake_blocking` against `DripPeer` (Read + Write + Timed). Setup mirrors the real caller: `DripPeer` starts with a read timeout of 5 s, exactly what `send_command_once` sets before the handshake on 1ccca49 (connection.rs:1118); that initial value is recorded separately from timeouts set by the helper. Each `read` sleeps `min(current read timeout, 4.9 s)`; if the sleep was cut by the timeout it returns `TimedOut`, otherwise ONE byte of a proof line that never ends. Asserts: `Err` mentioning the handshake timeout; total elapsed in [5.0 s, 5.3 s]; every timeout the helper set is non-increasing and no more than the time left. On 1ccca49 the helper never resets the timeout, the second read starts at ~4.9 s with the caller's fresh 5 s and returns at ~9.8 s: red by the elapsed assertion.
2. `native::daemon::control_tests::oversized_unterminated_frame_after_relayed_handshake_is_cut_off` (item 8). The rig's client completes a REAL handshake (`client_handshake_async`, standing in for a relayed one), then writes a valid-looking 86-byte `ab1` prefix followed by `COMMAND_PAYLOAD_MAX + 1 MiB` bytes of `a`, no newline, in 64 KiB chunks, under a 20 s guard. Asserts: a write fails (the daemon dropped the connection) before all bytes are accepted, with bytes accepted no more than `86 + COMMAND_PAYLOAD_MAX + 1 + BUFREADER_CAP + DUPLEX_CAP` (named test constants: the daemon `BufReader` capacity, 8192 by default, and the rig's 65536 duplex buffer); the `handle_connection` task has finished within 2 s of that; the idle clock was never marked and nothing executed. On 1ccca49 every byte is accepted into one `String` and the task never ends: red.
3. `native::daemon::control_tests::negative_counter_closes_the_connection_before_the_line_ends` (counter rule). After a real handshake the client writes only `ab1 -` and then holds the connection open; second case writes only `{"n":-1,` and holds. Asserts: the daemon closes (client read returns 0) within 500 ms, with no newline ever sent. On 1ccca49 the daemon waits for a newline forever: red.
4. `native::control_token::tests::item2_negative_counter_is_refused_without_panic` (item 2 regression). Item 2's code fix (`as_u64()?`) is already IN 1ccca49, so plain 1ccca49 is the fixed tree and a true regression test passes there by definition; its red proof is the revert. The test builds its vectors with the module-private `mac()` and the session key (never with `seal`), in the encoding of the tree under test: on 1ccca49 `{"n":-1,"m":"x","mac":HMAC(K, dir||0u64 BE||"x")}` (a MAC that is valid if a negative counter were ever coerced to 0); on rev B `ab1 +000000000000000 <HMAC(K, "ab1"||dir||0u64||"x")> x` and `ab1 -000000000000000 <same MAC> x` (a 16-character field: sign plus 15 zeros), likewise MAC'd for n = 0. Asserts: `open_bytes` returns `Err` for each, nothing panics, and a protocol-compatible control (a frame for n = 0 built by the same tree's `seal_bytes` on the peer session) then opens, proving no state advanced. ### B7. Threat boundary after rev B

Added to "kept out": a relaying squatter can no longer exhaust daemon, CLI or forwarder memory (each connection holds at most one capped line) or hold a handshake past `D_hs`, a client reply past `D_reply`, or a daemon frame past `D_frame`. Still possible and accepted: a relay can drop traffic, read it (no confidentiality claimed), or hold an authenticated connection for up to 30 s per frame wait; the number of such connections is bounded by legitimate client connections, because each needs a fresh real handshake to relay. Unix behaviour change (documented in the release note): Unix daemon command lines gain the 16 MiB cap (above the stream server's 10 MiB `MAX_BODY_SIZE`, so no forwarded body is accepted then refused), and the Unix CLI reply has one absolute `D_reply` instead of a fresh `read_timeout_for` per read.
