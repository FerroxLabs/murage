# G8 v7: configured Linux launcher and drained fixture

Run `g8-smooth.sh PRODUCT idle|load` on a Linux hub with a prepared test worker.
Set `G8_SSH_HOST` to the worker selected in your private SSH configuration and
`G8_HOST_ROOT` to its absolute scratch root. Optionally set `G8_SSH_IDENTITY`
to a local identity file; otherwise SSH uses its normal configuration. No
machine names, addresses, identity paths or private fixture inventories belong
in this repository. Use only fake engines and disposable data.

`G8_HUB` defaults to this checkout's Git directory; set it when using a separate
bare hub. `G8_RIG` defaults to HEAD. `G8_JOB` selects the local evidence directory
outside the checkout; its default is a temporary-directory sibling.
`G8_STATE` optionally names a new state directory under that job.

## Fixture preparation

The committed `fixtures-v7.json` is an unconfigured template. It deliberately
refuses launch until the operator supplies a private ready manifest, using
`G8_FIXTURE_MANIFEST` to name an absolute path on the worker. That file contains
`drained.status` (`ready`), `drained.archive` (an archive under the worker root's
`fixtures/` directory), and `drained.sha256` (the exact archive digest).
Keep manifests and captured evidence outside the repository.

Preserve the backlog fixture. Prepare a separate stopped working copy with the
normal product server and pinned fake engines, an empty home, temporary config
and networking disabled. `drain-fixture-offline.mjs` may call the product's
exported `drainRevokeMarker(database())` while that copy is stopped. The helper
uses product transitions rather than modifying job rows directly. Offline drain
is preparation, not proof of the background runner's performance.

Reboot the prepared copy through the normal fake-engine server. Require healthy
boot, zero active/undoing/seeding jobs and queued receipt flips throughout a
30-second window, graceful exit, and a second count after shutdown. Remove its
temporary config. Checkpoint SQLite WALs before archiving and refuse a nonempty
WAL. Record the archive digest in the private manifest. Each leg verifies that
digest and recounts work on a fresh extracted copy before running.

## Overlay and worker

`g8-overlay.sh` creates a commit parented by PRODUCT, overlaying only
`scripts/smoothness` and the five fake-engine files pinned by the script. It
uses a separate temporary Git index and records product, rig and fake revisions.
The ACP compatibility patch skips already patched fake engines and otherwise
runs noninteractively in forward-only mode.

Prepare dependencies under `G8_HOST_ROOT/gp18-nm/<lockfile hash>` and the native
cage under `G8_HOST_ROOT/cage/linux-x64` on the worker. A missing or mismatched
cache refuses the run. Docker uses `--pull=never` and `--network none`.

Run idle and load sequentially, including load when idle reports a gate failure.
Each leg uses a distinct data copy, six CPUs and 12 GiB. `PREBUILD=1` is the
default and builds the product's indexes before measurement. `PREBUILD=0`
does not make a drained snapshot a first-boot fixture.

The worker deadline defaults to 2400 seconds (`G8_TIMEOUT_SECONDS` overrides it).
SSH liveness checks and a separate outer deadline bound connection failure.
The worker removes only its own container, stress process, data copy and source
export on success, failure or TERM/HUP. Failed container removal retains mounts
and reports the error. Logs, reports and fixture hashes stay in the run directory.

The launcher records `worker.exit` and `tee.exit`; failed log persistence returns
4. `g8-wait.sh STATE TIMEOUT` follows both the launcher's PID and start time. It
fails on dead/reused launchers and times out even if PID publication never
happens. The contents of `done` are an exit status, not a product PASS verdict.

## Validation

Run `g8-launch.node-test.mjs` and `g8-deployment.node-test.mjs` with `node --test`.
They use command stand-ins and temporary files. `g8-host.node-test.mjs` also
needs Linux root, Python 3, tar and GNU timeout; it isolates everything under
`G8_HOST_ROOT` and uses a Docker stand-in. Smooth-config/smooth-gate and fake
engine suites run in a network-disabled container. Only completed full idle
and load legs establish a smoothness verdict.
