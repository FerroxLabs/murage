# B2 (feedback detection): patches for the integrator

server/memory/feedback.ts is self-contained and adds no shared-file edit. Wiring it needs three changes in shared or
cross-batch files, described here and NOT applied.

## 1. message-db.ts: a post-commit observer (the hook beside captureMessage)
captureMessage runs inside the message transaction (writeMessage, updateMessage), and detection is async (it may call the
learning connection), so it must run after commit. Add:

    let feedbackObserver: ((threadId: string, message: Message) => void) | null = null;
    export function setFeedbackObserver(fn: typeof feedbackObserver) { feedbackObserver = fn; }

and in insertMessage, appendMessage and updateMessage, after `transaction(...)` returns, for `message.role === "user" && message.kind === "text"`:
`try { feedbackObserver?.(threadId, message); } catch {}`. The observer must never throw into the write path.
detectFeedback is idempotent per owner message (row id = hash of thread + message id), so the updateMessage path and replays are safe and never repeat a model call.

## 2. server/index.ts: install the observer with real dependencies (search "learningDefaultOn")
    setFeedbackObserver((threadId, message) => void detectFeedback(database(), threadId, message, {
      classifier: connection.extractor ? learningConnectionClassifier(connection.extractor, () => readMemoryEvolutionPolicy().revision) : null,
      botLearning: id => { const b = store.getBot(id); return b ? readBotLearning(b) : null; },
      resolveBotId: (threadId, turn) => turn?.botId ?? rosterBotForThread(memoryCaptureRoster(), threadId),  // room: the replied-to bot; direct: the thread's bot
      readThread: (threadId, limit) => readThreadNewest(threadId, limit)?.messages ?? [],
      botName: id => store.getBot(id)?.name,
      lessons: lessonsService,          // B3 LessonSink; null until B3 lands (plan is returned, row stays "detected")
    }).then(emitFeedbackEvent, () => {}));
- `connection` is resolveLearningConnection(...) evaluated per call (key and selection can change). No connection -> classifier null -> stage 1 only (cap 2).
- The classifier call should go through the same per-minute learning budget as other learning requests (learning-policy.ts, MemoryInferenceLease). It is one request, at most 300 output tokens and about 2,000 input tokens, and only runs when stage 1 fires or the message replies to a bot message. On a budget refusal pass `classifier: null` for that call.
- resolveBotId: rooms/groups must use the prior turn's speaker (turn.botId); the roster lookup is for direct bot threads and their tasks.
- Optionally record a `feedback-detected` ledger event (kind exists in schema v5) for state "detected" and "lesson"; B3 widens recordLearningEvent's kind union first.

## 3. B3 (lessons service) contract
- Implement `LessonSink.form(plan, {botId, threadId}) => lessonId | null`. plan.askFirst true -> state "suggested", else "active" and a memory_learning_events row first, same transaction (INVALID_MEMORY_LESSON_EVENT otherwise).
- Store `plan.evidence` as the lesson's `evidence` JSON unchanged: `{feedbackId, phrase, messageId, action}`. suppressedPhrases() and isBlockedLesson() read `evidence.phrase`, `state='undone'` and `decided_at` from memory_lessons. When the owner undoes a lesson, set state 'undone' and decided_at.
- On form success detectFeedback calls markFeedbackLesson (feedback row state -> 'lesson', scope 'bot'). For the Unsure row action ("Yes, that was feedback") call confirmUnsureFeedback(db, id), then planFeedbackLesson(...) with the stored row.
- Edit-on-repeat: B1 captures the draft edit; call classifyEdit(before, after) then planEditLesson(botId, kinds, priorCounts, {askFirst}) with counts of earlier edits of each kind.
- "Recent feedback" block: recentThreadFeedback(db, botId, threadId) returns at most 3 rows (detected or lesson). The 20-turn expiry is B3's.
- Chip rate limits (praise 1 per 10 turns, none for strength 1 / unsure) belong to the chip component (B3); this file only supplies strength and state.
