1. **High — R5; ordinary replay row; test 3.** Keeping ordinary failed lines in replay violates the ruling. `server/index.ts:12021` excludes the current batch, not earlier failed sends. After A fails, unrelated B can receive A through history; an explicit new A can receive both the old A in history and the new A as its prompt. R2 prevents same-ID replacement, not replay. **Change:** exclude all definitively unsubmitted failed lines from automatic replay, including ordinary sends and `lateRefused` lines. Preserve history for turns that actually received their words. Reverse test 3's ordinary-line expectation.

2. **High — R1; background-failure row; test 1.** `onDispatchError` does not cover every background startup failure. ACP returns a turn ID before asynchronous session setup finishes (`server/drivers/acp/core.ts:5807`); setup rejection emits `runtime.error` and settles the provider turn (`server/drivers/acp/core.ts:5733`), without rejecting the already-returned dispatch promise. The proposed fake ACP setup failure can therefore remain broken after R1. **Change:** settle the originating send batch on terminal, proven-unwritten provider setup failures too, before releasing its thread. Test both a rejected server dispatch and an accepted ACP turn whose session setup subsequently fails.

3. **High — R1; memory-rebuild row.** "Only the last failure reaches onDispatchError" misses the late-submission rebuild path. Its terminal `settleWithCard` writes an activity line but never invokes that callback (`server/index.ts:13542`). Exhausted rebuilds, a missing held run, and a rebuild that cannot start can finish through that path (`server/index.ts:13561`, `server/index.ts:13573`). Rows can remain `started`. **Change:** route every definitive terminal rebuild outcome through the same batch settlement, while successful or pending rebuilds retain `started`. Add exhaustion, rejected-redispatch, and Stop-during-rebuild cases.

4. **High — R1/R5; restart reachability.** Startup recovery does not reconcile `started` or `failed` rows: its unresolved selection contains only `dispatched` and `unconfirmed` (`server/send-store.ts:894`). A crash after the error line but before the proposed callback, or an existing stranded `started` row, survives restart and still answers `unknown` (`server/index.ts:15798`). R5 also misses that row. **Change:** persist terminal failure and its receipt atomically; specify recovery for orphaned starts using durable submission evidence. Preserve genuinely uncertain outcomes without redispatch, and prevent their unsubmitted lines from entering unrelated replay. Test restart at these boundaries.

5. **High — R1/R5; Stop and intervening-turn reachability.** Settlement can occur after another turn has already built its replay. Stop can release a setup run while its asynchronous setup is still pending (`server/index.ts:2889`); the failure callback arrives later at `server/index.ts:13662`. Likewise, `freeThreadAfterRebuild` drains queued work before the enclosing failure handler settles the failed batch (`server/index.ts:2616`). During that gap, R5 sees `started`, not `failed`. **Change:** establish durable replay ineligibility before releasing a proven-unsubmitted run, or mark such lines ineligible from initial append until submission succeeds. Test Stop with suspended setup, a subsequent send, and late setup completion.

6. **High — R2/R5; retry and isolated-replay "Unreachable" claims.** Both guarantees disappear when ledger pruning runs. Failed-with-line rows are prunable (`server/send-store.ts:231`) after 30 days or under the 5,000-row cap (`server/send-store.ts:225`, `server/send-store.ts:939`). R5 then forgets the exclusion. R2 loses its guard; the fallback checks only recent transcript rows (`server/index.ts:15840`), so an older same-ID retry can become a new send. **Change:** retain indexed deduplication and replay-exclusion facts independently of the prunable ledger, preferably alongside the kept transcript line. Add age/cap pruning followed by restart, replay, and same-ID retry tests.

7. **Medium — R2; "every route"; room exclusion.** The room justification is inaccurate. There is also an `owner_sends` channel drain (`server/channel-queue.ts:121`, `server/index.ts:19986`), including room question-card answers (`server/index.ts:7087`). Moreover, the group POST route implements its own failed-row reopening and retirement, bypassing `SendStore.accept` on its idle and room-request paths (`server/index.ts:27605`, `server/index.ts:27665`). **Change:** explicitly document both room mechanisms. If R2 remains universal, enforce failed-with-line receipts before those reopening branches and prevent retirement of such rows; add group-route coverage. Otherwise narrow the claimed scope and remove "every route."

8. **Medium — R1; error-line guarantee.** The callback is also reached through `giveBackAdmittedTurn.report` (`server/index.ts:13737`, `server/index.ts:13766`). That path handles failures in setup's own failure handling and does not guarantee an activity line already exists. `giveBackAdmitted` reports independently of cleanup failures (`server/admitted-turn.ts:84`). Consequently, "onDispatchError writes none" can hand the person to a chat with no explanation. **Change:** distinguish already-reported failures from fallback reports and write one deduplicated explanation when needed. Ensure failure settlement still runs if writing the explanation throws.

9. **Medium — R4; existing receipt.** The claimed receipt behavior is not current code. An existing failed-with-line row falls through to `{ok:true, steered:true, message}` without a failed state (`server/index.ts:15892`). The outbox treats it as acknowledged (`src/state/send-delivery.ts:339`), and the Help callback receives no failure field (`src/state/store.tsx:5186`). It will stop retrying, but the receipt itself does not say the turn failed. **Change:** specify the exact receipt contract. Either explicitly rely on acknowledged delivery plus turn-state polling, or add and propagate a failed outcome through the receipt types and Help reader. Test the actual lost-acknowledgement retry end to end.

10. **Medium — R6; cancellation across receipt paths.** The proposed turn-state mapping is sound, but a cancelled send acknowledged through POST follows a different path: `receiptChange` maps cancellation to `"missing"` (`src/components/help/HelpAsk.tsx:183`). That view stops following, so R6's new polling response cannot correct it. **Change:** map a confirmed cancelled receipt to `"removed"` too. Place the server's cancelled-state check before the missing-`messageId` return (`server/index.ts:15798`), and test both an already-acknowledged queued send and a lost-acknowledgement retry after removal.

11. **Medium — R1; first state row.** The unconditional "Before: failed + line" is false for sends without a send ID. Current `onFail` finds rows only through the transcript line's `sendId` (`server/index.ts:11097`), although queued sends can omit it (`server/steer-queue.ts:64`). Such rows remain `started`. **Change:** define batch settlement using captured ledger sequence IDs, or the persisted queue ID, rather than requiring a client send ID. Add an anonymous-send batch case and qualify the current-state description.

12. **Medium — R5; scale claim.** The proposed query is not bounded specifically by failed help questions. The existing index is `(thread_id, status, seq)` (`server/send-store.ts:279`); `isolated` and `message_id` are residual filters. It can scan every failed row in the thread, including receiptless failed rows that pruning retains. **Change:** require a matching partial index, or evaluate durable replay eligibility against the bounded replay candidates. Replace the claimed bound with the actual query bound and add query-plan coverage.

13. **Medium — tests 1–6; "each fails on current code."** Test 5's stated defect is already fixed: successful loading resets the retry budget (`src/components/help/HelpAsk.tsx:411`), with existing source coverage at `src/components/help/HelpAsk.test.ts:587`. A faithful mounted test should pass current code. Tests 1, 3, 4, and 6 can expose current defects; test 2 can fail for unguarded retries, but replaying the same recorded `actionId` already returns `existing` (`server/send-store.ts:620`). **Change:** label test 5 as behavioral coverage of an existing fix; separate test 2's already-passing controls from its failing cases. Make test 3 force actual replay into a fresh session, and make test 6 exercise the callback wired by the mounted component. Extend coverage for the failure paths and boundaries above.

14. **Low — state-table accuracy, especially rows 4–6.** A successful drained dispatch stamps `dispatchedIn` without changing its ledger row to `delivered` (`server/index.ts:2634`); `started + dispatchedIn` is normal. Also, current failed-row replacement is conditional on fingerprint, restore, Stop, and action-token checks (`server/send-store.ts:610`). **Change:** split "delivered" from "started with a dispatch stamp," and qualify the retry "Before" cells. Keep the new-send and failed-without-line chip rows: R2's proposed guard does not intercept those flows. The `lateRefused` change correctly removes same-ID reruns, but its replay guarantee requires finding 1's fix.
