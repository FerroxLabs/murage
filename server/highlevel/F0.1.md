# F0.1 expected-target settlement amendment

Additive amendment to F0 `953a1d82200c27b4c1814236a7be22e2b54e6b58`.
Only these public signatures are added in `operations/registry.ts`:

```ts
// SpecBase<A = Record<string, unknown>>
project(value: unknown, frozen: FrozenRequest): unknown;
// MutationSpec<A = Record<string, unknown>>
recordId?(value: unknown, frozen: FrozenRequest): string | undefined;
```

`FrozenRequest` is imported from `server/highlevel/held-request.ts`. The
one-argument overloads remain and carry `@deprecated` JSDoc for a TypeScript
editor/language-service migration nudge. They do not produce a tsc error.
Existing one-argument implementations still compile. New implementations can
use `frozen?: FrozenRequest` to satisfy both overloads, but mutation validation
must refuse absent context. Plain reads may retain their one-argument call.
Source compatibility does not make an unmigrated mutation safe to enable.

## Approval and dispatch binding (C2)

`HighLevelActions.beginDispatch(actionId, current)` keeps its F0 signature:
`{ intent: ActionIntent; held: HeldRequest }`. It must verify the action's
approval/review digest, current authority and retained request binding before
returning. The operation, resource, body hash, upload metadata and request
digest must agree with the approved intent; the selected spec must match
`held.frozen.operation`. A `FrozenRequest` type alone is not proof of approval.

Retain that exact `held` for the entire dispatch. Pass it to
`sendFrozen(client, ctx, held, intent.requestDigest)`, which independently
verifies the wire bytes, content type, v2 request digest and upload range hash
as required by F0. Do not freeze again, reconstruct a target from tool arguments,
use a response ID as the expected ID, or use mutable state on a shared spec.

After send, while still within the authority/release guard, the required order is:

1. Validate the raw response with `spec.recordId?.(value, held.frozen)`.
2. Validate/project with `spec.project(value, held.frozen)` using the same exact
   retained request object. Never project or emit provider response values
   before identity validation succeeds.
3. Only after both hooks and the release/authority checks succeed, settle
   `applied` once and publish the validated result/receipt. The receipt ID, if
   present, comes from successful validation; never substitute the expected ID
   to disguise a mismatched or missing provider ID.

`recordId` remains optional. Where omitted, `project` must perform the operation's
identity and success validation before returning or releasing anything.
An `undefined` record ID alone is not evidence of success. Operations with no
receipt ID require their documented explicit success confirmation. The F0
`applied(actionId, { recordId, fields })` signature is unchanged: C2's existing
empty-string receipt ID may represent no ID only after that validation, and
must not be published as a provider ID. Do not invent a record ID.

An identity mismatch, conflicting parent, malformed response or missing required
confirmation after send is `outcome_unknown`, not `applied` or proof of
`not_applied`. Withhold the response/receipt, settle once, and never resend
automatically. Preserve an already terminal `stale` decision. This amendment
does not relax one-send, durable recovery, policy approval or authority checks.

## Expected targets (family owners)

Derive expected identities from the approval-verified frozen path/resource
using the operation's declared route, not a generic last-path-segment heuristic.
Check the operation and route before extracting IDs. The existing request
digest binds path, resource and query; there is no new target field or digest
version. Validate every returned identity used by the response contract,
including conflicting aliases/envelopes and reported parent identities.

| Operation | Required identity rule |
| --- | --- |
| `contacts.update` | Returned contact ID equals the contact in the approved path. |
| `contacts.notes.update` | Returned note ID equals the approved child ID; any reported contact ID equals the approved parent. |
| `contacts.tasks.update`, `contacts.tasks.complete` | Returned task ID equals the approved child ID; any reported contact ID equals the approved parent. Completion's trailing route action is not a task ID. |
| `opportunities.update` | Returned opportunity ID equals the approved opportunity ID. |
| `opportunities.pipelines.update` | Returned pipeline ID equals the approved pipeline ID. |

Create operations may return a new valid ID: do not compare it to a parent or
location resource. Still validate any reported parent/location against the
retained request. Upserts use their operation-specific identity/confirmation
contract; do not invent an expected existing ID. Deletes and follower mutations
must validate their documented success response even when no record ID is
returned. In particular, `followers.add/remove` must reject `{}` and
`{success:false}` as unconfirmed and settle `outcome_unknown` after send.

## Migration and evidence

- hlf1: migrate registered contact/note/task `recordId` and `project` hooks;
  refuse missing context, wrong child/contact IDs and conflicting parents.
  Run all four retained wrong-ID RED probes with the frozen context, plus
  valid targets, creates and interleaved prepares to exclude shared state.
- hlf2: migrate registered opportunity/pipeline hooks to the frozen context;
  wire expected-ID validation into the registered path rather than a detached
  helper. Run all four retained RED probes and valid targets. Add follower
  malformed/negative confirmation tests independently of the ID amendment.
- hlc2: implement the dispatch order and binding above in the production host.
  Verify with isolated fake-provider fixtures through approval and actual held
  dispatch: wrong IDs/parents and malformed followers cannot project or settle
  applied; swapped/reconstructed contexts refuse; valid responses settle once.
  Retain approval/policy, stale-authority, concurrent-send, timeout and
  restart/replay coverage. Do not replace these with manual settlement tests.
- hlc3: adopt the F0.1 snapshot/docs when integrating; preserve existing frozen
  upload/send-copy and anchored-reader contracts. No anchored-reader signature
  change is required. Re-run snapshot and types with hlc2; retain native/package
  proof obligations. This response amendment supplies no native execution proof.

F0.1 tests pin both overloads, the deprecation nudge and F0 source compatibility.
Removing only these two additions must reproduce F0's exact snapshot hash,
including every original signature and manifest/schema hash. Both TypeScript
configs must pass. This contract amendment does not implement family hooks or
C2/hlc3 runtime stubs and does not close their production safety findings.
