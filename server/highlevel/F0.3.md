# F0.3 — portable durable approval journal

Additive to F0.2 (`ae2df96031117c2d78a525b9f9f945b3771655c6`). F0.1/F0.2
snapshots, public signatures, record layout, filenames, and call sites are
unchanged. This document supersedes only F0.2's filesystem/platform limitation.
Existing pending and terminal records remain readable without migration.

## Commit and replay

`FileApprovalJournal(directory)` still stores an immutable pending record and
an immutable first terminal outcome per approvalId. Publication is:

1. Write a unique, exclusively created temp file in the journal directory.
2. Flush its writable file descriptor before publication.
3. Hard-link it to the final name atomically, without replacing an existing
   name. `EEXIST` loses the claim; it never overwrites a competing digest/result.
4. Flush the still-open file descriptor again. On POSIX, fsync the directory.
5. Close the descriptor and remove the disposable temp name.

Windows NTFS supports this hard-link path, explicitly permitted by F0.3's
requirements. No rename fallback is needed on NTFS. A replace-rename of the
final name would violate atomic insert-if-absent and immutable first outcome;
there is no check-then-rename race in this implementation. The crash test named
`before-publication` is the write-to-link boundary, equivalent to the requested
write-to-rename boundary for the permitted hard-link path.

On win32, Node's `fsyncSync` invokes FlushFileBuffers. No directory is opened or
fsynced. On darwin, Node 24/libuv attempts F_FULLFSYNC, then F_BARRIERFSYNC, then
fsync if unsupported; Node has no separate public fcntl API to call here. Linux
uses fsync. POSIX initialization also flushes directory ancestors on the same volume,
including on retry after a failed creation barrier; it stops at the volume
boundary, without touching macOS's separate read-only system volume.

Reopening a visible entry completes its file/directory barriers before returning
it: a publisher may have exited after linking and before its last barrier.
Flush failures prevent dispatch and replay success. Pending always means
read-only reconciliation, never another send. Torn/unpublished temps are ignored;
cleanup failure may leave an inert unique temp but cannot mask the commit result.
Committed corrupt records still fail closed. No records are aged out.

Native implementations checked against Node 24 sources:
- [Windows fsync, hard link and rename](https://github.com/nodejs/node/blob/v24.x/deps/uv/src/win/fs.c)
- [Darwin full flush and fallback](https://github.com/nodejs/node/blob/v24.x/deps/uv/src/unix/fs.c)

## Filesystem checks and owner errors

Windows queries the resolved volume with built-in Windows PowerShell and
GetVolumePathName/GetVolumeInformation/GetDriveType. Local fixed/removable NTFS
is accepted; FAT/exFAT, UNC/network and mapped remote volumes are rejected.
The directory is base64 stdin data, never interpolated executable text. Node's
Windows statfs type is zero, so it cannot implement this check alone. No admin
privileges, optional packages, credentials or provider access are required.

Darwin resolves the longest enclosing mount, checks its local flag, and rejects
FAT/exFAT/network mounts. Numeric filesystem types are dynamically assigned, so
an APFS numeric constant is not used. Linux rejects FAT/exFAT, known network
filesystem types (including remote FUSE subtypes) and volatile tmpfs. Other local
filesystems must support atomic hard links and durable sync; errors are surfaced
without a weaker fallback. Hardware/storage must honor the OS flush primitives.

Unsupported storage raises an owner-readable `HighLevel approval journal ...`
error instructing the owner to use local NTFS/APFS/durable Linux app data storage.
IO, permissions, probe and flush failures also raise actionable errors; they do
not silently claim durability or dispatch. Host integration should display this
error through its existing error surface. F0.3 proves the primitive, not a family
UI or production integration.

## Adoption

hlf1, hlf2 and hlc2 can adopt F0.2 immediately. Keep all F0.2 binder, authority,
request digest, projected receipt and reconciliation obligations. F0.3 only
changes the storage implementation beneath the identical API; no call-site
migration or new arguments. No platform-wide HighLevel hold is introduced.

## Verification and Windows handoff

Linux container tests inject filesystem operations and OS/platform probes to run
all three branches: pre-publication flush ordering, NTFS without directory opens,
POSIX barriers, torn temps, crash boundaries, immutable duplicate IDs/outcomes,
post-publication flush failure/retry, and unsupported-volume guidance. This injected-fs suite is classified for Linux; the existing approval-idempotency
suite now runs on all three OSes. The actual
F_FULLFSYNC/FlushFileBuffers syscalls require their native operating systems.
The dependency-free native runner adds real child-process termination and a
simultaneous two-process duplicate claim. These are process-crash tests, not a
physical power-cut/hardware certification.

MAIN on the Windows Desktop PC, checkout at `C:\murage-ci` on NTFS with Node 24+:

```powershell
powershell -NoProfile -File C:\murage-ci\scripts\highlevel-f03-windows.ps1
```

The script records SHA and output under `C:\murage-ci\evidence\f03-windows`,
creates and removes only its own isolated temp data, and makes no provider calls.
Expected output (timing/version warnings may vary):

```text
PASS native torn
PASS native before-publication
PASS native after-publication
PASS native duplicate-approvalId (2 processes; 1 winner; immutable outcome)
PASS native total=4 platform=win32
PASS F0.3 Windows NTFS; no live app or provider used
```

`native.rc` must contain `0`. A failure is an OPEN verification item, not a reason
to add a Windows feature hold. Native Windows/macOS results must not be claimed
from Linux injection results. The same Node runner can be run directly on APFS.
