# F0.2.2 RPC recovery and operation confirmation

Additive to F0.2.1 (`032a7cd02affd787bc31b95da1e5b7c96f61eeb3`). All F0.1/F0.2
public signatures, wire schemas, projections and identity policy hashes remain
unchanged. `frozen-f022-contract.json` freezes the new APIs separately.

## RPC association in the approval journal

Use `FileRpcApprovalJournal(directory)` from `rpc-approval-replay.ts` in place
of `FileApprovalJournal` at the same approval directory. It inherits the old
API and reads existing approval records unchanged. Its extra immutable
`*.rpc.json` entries contain `RpcApprovalBinding`: RPC id/digest, original
approval id/request digest, action id, authority digest, operation, concrete
read targets and an expected-effect digest. There are no review values, wire
bodies, credentials or raw provider responses in this index.

`runRpcApprovedWrite(journal, rpcId, rpcDigest, callbacks)` replaces the outer
RPC `runApprovedWrite` wrapper. Its callbacks are:

- `prepare()`: perform proposal/review/current-authority verification and return
  the association. **Do not send here.** Derive read targets from the retained
  approved request, never replay arguments. `effectDigest` hashes the canonical
  operation-specific expected effect, using the action's durable field names
  to select the fields. For sets, canonicalize order before hashing. A target
  must be a concrete read in the mutation's declared reconciliation list.
  F0.2.4 requires a nonempty list before approval; unsupported recovery refuses
  approval. Qualified R searches may use POST; arbitrary writes are not reads.
- `authorize(binding)`: verify the action, approval id, review/request binding,
  connection epoch, location, grant, policy, role and current turn authority.
  This runs before work and again before release, including cached outcomes.
  Recovered `outcome_unknown` is eligible for **read-only reconciliation**, not
  a new dispatch. Existing `stale` is never revived.
- `dispatch(binding)`: the first-dispatch path only. Call `beginDispatch`,
  prepare the response identity/confirmation schema, record attempts and send
  the exact retained request. Validate the whole response, operation semantics,
  projection and current authority before returning a safe receipt/result.
- `reconcile(binding)`: use `binding.readTargets` through the existing authorized
  read transport. Validate all returned identities, then compare the actual
  operation-specific effect with `binding.effectDigest`. Target existence or
  writable preconditions do not prove the effect. Return applied only with
  proof; `conflict/negative_confirmation` only with proof of non-application;
  otherwise `conflict/unconfirmed`. Exceptions retain pending. Never send or
  prepare a new approval from this callback.

The association is fsynced before the approval's pending claim and before
`dispatch`. Reopening a pending RPC resolves the original approval. A pending
approval takes `reconcile`; an existing terminal approval returns its persisted
outcome. A crash after association publication but before the approval claim
also takes `reconcile`, even though no write may have left. Same-process
concurrent RPCs share preparation and execution. Cross-process association
publication is atomic and first-writer-wins; losing publishers cannot dispatch.
The existing F0.2 cross-process pending/read semantics still apply.

There is no separate RPC outcome cache. Approval settlement stays immutable
and precedes action settlement/publication. Map `conflict/negative_confirmation`
to action `not_applied`; other conflicts remain withheld/outcome_unknown, with
stale preserved. After a crash following approval settlement, apply the stored
receipt to the **original** action (idempotently) after authority verification.
Do not call `beginDispatch` or require a retained body to release that receipt.

A legacy outer-RPC pending record with no association cannot identify an
approval. The helper leaves it pending and returns unconfirmed without a new
review or dispatch. If a lane can prove the old mapping from durable data, it
may call `bindRpc` to install it; it must not guess, clear the pending record or
blanket-settle it. Corrupt associations fail closed before callbacks. The file
backend retains F0.2's hard-link and directory-fsync platform requirements.

## Operation-specific confirmation

`operations/returned-confirmation-schemas.ts` declares a confirmation policy for
every operation. `contacts.tags.add` and `contacts.tags.remove` declare
`tag_post_state`; other operations retain `identity_or_success`. This is an
additive portion of the operation schema, separate from the frozen identity
schema. No response fixture needs an invented success flag.

For tag mutations use:

```ts
const bound = prepareTagReturnedIdentitySchema(held, locationId, beforeTags);
const checked = bindReturnedIdentities(rawResponse, held.frozen, bound);
```

Import the adapter from `returned-confirmation.ts`. `beforeTags` must be the
complete set from the identity-validated preflight for the approved contact,
retained with that approval. Missing or malformed pre-state must refuse; do
not substitute `[]`. The adapter verifies the retained wire body and computes
union for add, difference for remove. Expected sets are immutable and bound to
the exact frozen object. Rebinding that object to a different expectation
refuses. Later ordinary `prepareReturnedIdentitySchema` calls on the same object
do not clear the expectation. Existing family hooks still retrieve it through
`returnedIdentitySchemaFor(frozen)`.

The gate requires root `tags` to equal the entire expected post-state, ignoring
order but rejecting duplicates, extras, omissions and non-string entries.
Every repeated tags set must agree. A generic success flag or approved contact
id cannot bypass this requirement. The full response walker always runs: a
foreign contact id anywhere is conflict, unknown identity keys are logged by
name only, and negative confirmations still produce not-applied. No post-state
preparation means fail-closed even with a success flag.

A correct tag-only response thus confirms `{tags:["a"]}` after adding `a` to
an empty set and `{tags:[]}` after removing `a` from `["a"]`. On recovery, use
the durable expected-effect digest and read targets; do not use the new current
tags as a replacement pre-state to reconstruct an old approval.
