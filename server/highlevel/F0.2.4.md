## Approval and recovery contract

Every write row in `operations/manifest-data.json` now declares `reconciliation`.
`reconciliationReadsFor(operation)` returns the immutable qualified read list,
or refuses when unavailable. Prerequisite reads remain in `preflight`; adding
an effect read there also authorizes the existing bounded read transport.
A prerequisite alone (for example custom-field definitions for contact create)
is not a reconciliation declaration. Read operations are selected by R risk,
including qualified POST searches, never by allowing arbitrary POST requests.

`rpc-approval-replay.ts` refuses an empty `readTargets` array immediately after
prepare, before authorize, RPC publication, approval claim or dispatch. Every
target must belong to the operation's reconciliation declaration and match the
read's concrete route. Existing RPCs with empty targets fail closed on load;
they cannot be silently reapproved or resent. Public F0.1/F0.2/F0.2.2/F0.2.3
signatures, wire schemas and identity policies are unchanged. MAIN explicitly
amends the manifest hash; current snapshot and historical compatibility tests
check that this is the only exception. F0.2.4 freezes its additive lookup API.

`courses.import` retains its qualified provider endpoint but declares
`approvalBlocked: reconciliation_unavailable`: its only course-list read is
provider_absent. It cannot approve until that read is qualified and the block
is explicitly removed. Provider-absent operations also remain unapprovable.
An unavailable reader must never be replaced by an unrelated successful read.

Before returning an approval binding, derive concrete targets, approved field
selectors, expected-effect digest and necessary parent/location context from
the verified held request and durable action. Never derive them from replay
arguments or a provider response. Target IDs belong in the existing durable
readTargets; raw reviewed values do not belong in that index. Refuse approval
if the lane cannot construct a usable plan. Each caller checks current authority
before reads and result release. The transport uses the declaration's actual
method and schema; location/query/body parameters come from verified durable
context. A read declaration does not grant authority across locations.

Creates without a known ID use a collection/search read and filter candidates
by all approved identifying/effect fields. For pipelines.create: one authorized
GET `/opportunities/pipelines`, scoped by the durable action location, then
compare exact name AND stages (including approved stage positions and any other
approved stage fields) against the approved effect digest. Ignore new provider
IDs only in schema-declared creation slots; retain the full-response identity
and negative-confirmation checks before projection/settlement. One proven unique
match can confirm applied. An authoritative complete read proving absence of
the effect can give conflict/negative_confirmation, mapped to not_applied.
Ambiguous matches, incomplete pagination, absent required fields, unavailable
reads or insufficient causal evidence remain unconfirmed. Do not infer creation
merely from a pre-existing match. Never resend on recovery. The isolated witness
uses a complete fake collection with known pre-state; exactly one read suffices
there. Other collections may need bounded pagination; no universal one-read
claim is made.

F0.2.3 ownership still starts synchronously as soon as the approval is available,
before the first post-approval await, keyed by approval-journal identity plus
approvalId. Adopt `runRpcApprovedWrite` as the sole owner where possible. Manual
paths use `runApprovedInvocation` around their single `runApprovedWrite`. Never
wrap or recursively call a same-approval owner from its own dispatch. Prepare
must return the association immediately after synchronous binding construction;
post-approval asynchronous authority checks belong in authorize/dispatch.
