# F0.2 structural identities and approval replay

Additive implementation on F0.1 `80218398073cd80eb70ed0b262d86d2964bf3ddc`.
All original public signatures, manifest rows, argument/wire schemas and the
F0.1 snapshot remain byte-for-byte unchanged. New declarations are frozen in
`frozen-f02-contract.json`; `scripts/highlevel-f02-snapshot.ts` checks them.

## Shared identity gate

```ts
// server/highlevel/returned-identities.ts
prepareReturnedIdentitySchema(held: HeldRequest, locationId: string): BoundReturnedIdentitySchema;
returnedIdentitySchemaFor(frozen: FrozenRequest): BoundReturnedIdentitySchema;
bindReturnedIdentities(response: unknown, frozen: FrozenRequest,
  opSchema: BoundReturnedIdentitySchema): ReturnedIdentityResult;
```

`prepareReturnedIdentitySchema` must receive the exact retained held request
returned by approval/current-authority verification, plus the connected location
from that verified context. It verifies the v2 digest, operation, route, method
and wire body hash. It derives approved identities from the declared route,
frozen query and retained JSON or multipart bytes. It checks connected location
against any reported request location. It never reconstructs the request from
current tool arguments. The returned schema is immutable and tied to that exact
`FrozenRequest` object; copying or forging it refuses. It contains no public
approved ID values. It is also retained in a WeakMap keyed by that exact frozen object.
Existing two-argument family hooks call `returnedIdentitySchemaFor(frozen)` to
retrieve it, then `bindReturnedIdentities(value, frozen, opSchema)`. Missing
preparation or a copied context throws; interleaved requests cannot replace each
other. Re-preparation for a different connected location refuses. No signature
changes to `recordId(value, frozen)` or `project(value, frozen)` are needed.
Cache it only for that dispatch, never in shared family state.

`FrozenRequest` deliberately remains unchanged: its body hash alone cannot
supply approved followers, assignees, custom fields or stage IDs. Preparing the
bound schema from the retained bytes solves this without adding mutable context
to the frozen interface or requiring existing callers to change signatures.

The binder walks the entire raw JSON response, including every object in every
array, using an iterative walk. It checks `id`, `*Id`, `*_id`, plural ID forms,
assignees, follower/user references, and schema-declared identity fields.
Bare `id` uses the nearest declared resource container's role; otherwise it uses
the operation's primary role. An approved ID in a different role is insufficient.
Unknown identity-shaped fields refuse even in discarded projection fields. The
only diagnostic output is the unknown key name itself; values, paths, responses
and provider error strings are never returned or logged.

`operations/returned-identity-policy.json` explicitly lists **every manifest
operation**, including unavailable operations, with its primary role and created
slots. `HIGHLEVEL_RETURNED_IDENTITY_SCHEMAS` adds identity declarations from the
actual frozen argument/wire schemas and route, plus the connected-location
pass-through. Missing declarations fail closed. Provider-absent operations and
plain reads cannot prepare an approved-write binding. Read results continue to
use the existing read authority and projection contracts.

A new ID is accepted only in an exact declared response slot (array wildcard
matches only an index). Creation aliases must agree; newly created children
cannot reuse each other's IDs or any approved related ID. Upsert without an
approved primary ID requires root `new:true`; `new:false` with an unapproved
existing ID refuses. New pipeline stages require the corresponding approved
request stage to omit an ID; replacing an existing stage ID refuses. Undeclared
provider identity fields need a reviewed schema amendment, never a wildcard
pass-through. This intentionally withholds unfamiliar provider response shapes.

Negative confirmations anywhere return `not_applied`, including false success
flags, nonempty errors, positive error counts, failing status codes/statuses,
and `deleted:false` on DELETE. Identity conflicts take precedence if both occur.
Malformed confirmation flags, cyclic/non-JSON objects, and missing positive
confirmation refuse. Follower mutations require a confirmed set exactly equal
to the frozen request set, with no duplicates, extras, omissions or inconsistent
object aliases. Every repeated follower set is checked, including nested ones.
An upsert with a supplied follower set must confirm that set as well.

The result has no provider payload:

```ts
type ReturnedIdentityResult =
  | { readonly status: "applied" }
  | { readonly status: "not_applied"; readonly reason: "negative_confirmation" }
  | { readonly status: "conflict"; readonly reason: "request_binding" |
      "unknown_identity" | "identity_mismatch" | "follower_set" |
      "unconfirmed" | "malformed_response"; readonly keys: readonly string[] };
```

`applied` is the shared identity/confirmation gate, not permission to settle or
release data. Operation-specific response shape/semantic checks, projection,
release and current-authority checks still must succeed. On `conflict`, project
nothing and publish no receipt. On `not_applied`, project nothing and settle
not-applied. This supersedes F0.1's per-field identity-checking prescription;
its authority, retained-request, release and stale-preservation rules remain.

## Durable approval subjournal

```ts
// server/highlevel/approval-idempotency.ts
new FileApprovalJournal(directory: string): FileApprovalJournal;
runApprovedWrite(journal: ApprovalJournal, approvalId: string,
  requestDigest: string, callbacks: ApprovedWriteCallbacks): Promise<ApprovalOutcome>;
```

Create one dedicated approval subjournal under the application's data directory,
for example `highlevel/approvals`. It is separate from the legacy action journal,
so no old journal signature/parser changes are needed. The record is keyed by
approval ID and bound to the verified frozen request digest:

```ts
type ApprovalIdempotencyRecord = {
  readonly approvalId: string; readonly requestDigest: string;
} & (
  | { readonly state: "pending" }
  | { readonly state: "applied"; readonly result: unknown }
  | { readonly state: "conflict"; readonly reason: ApprovalConflictReason }
);
type ApprovalConflictReason = "approval_binding" | "identity_conflict" |
  "negative_confirmation" | "unconfirmed" | "authority_changed";
type ApprovalOutcome = { readonly status: "applied"; readonly result: unknown }
  | { readonly status: "conflict"; readonly reason: ApprovalConflictReason };
interface ApprovedWriteCallbacks {
  dispatch(): Promise<ApprovalOutcome>;
  reconcile(): Promise<ApprovalOutcome>;
}
interface ApprovalJournal {
  readonly key: string;
  get(approvalId: string): ApprovalIdempotencyRecord | undefined;
  claim(approvalId: string, requestDigest: string): boolean;
  settle(approvalId: string, requestDigest: string, outcome: ApprovalOutcome): ApprovalOutcome;
}
```

`claim` atomically publishes a fully written and fsynced pending entry before
send. Terminal entries are likewise atomically published and immutable; first
terminal outcome wins. File and directory fsync failures refuse. Corruption or
a torn published record refuses rather than becoming a never-seen approval.
This file implementation targets filesystems supporting hard links and directory
fsync (Linux/macOS); use an equivalently durable `ApprovalJournal` adapter on
other platforms. Do not weaken atomic claims to get an unsupported filesystem
working. The API has no delete/expiry path that can accidentally re-enable send.

`runApprovedWrite` dispatches only the winner of the first claim. Repeated calls
return the stored outcome without dispatch. In-process concurrent callers share
the pending promise, even through separate file-journal instances for the same
resolved directory. A pending entry after process loss invokes `reconcile`,
which MUST use reads only; no reconciliation result permits a resend. A separate
process encountering pending may read concurrently with the first process, but
cannot dispatch; terminal publication still uses first-writer-wins semantics.
An unavailable/ambiguous effect returns `conflict/unconfirmed`. Exceptions leave
pending, so the next replay remains read-only. Reuse of an approval ID with a
different request digest refuses before callbacks. A deliberate fresh write
requires a fresh review and approval ID.

The reconcile callback must reuse the existing recheck/read transport path and
establish the **actual approved effect**, with identity and semantic validation.
The old `RecheckResult {ok:true}` only establishes permission/preconditions for
some operations; it is not by itself proof the write happened. For an operation
whose effect cannot be established safely by read, persist conflict and withhold.
Do not convert an inconclusive read into a resend.

Only store an already validated, projected safe result/receipt in `result`.
Never store raw provider responses, credentials, exception messages or review
values. Results are JSON-only and cloned on return. Persist the terminal outcome
before action settlement/publication. Preserve any preexisting `stale` action;
a stored outcome never grants current authority to release data.

## Exact adoption obligations

- **hlf1:** delete the per-field returned-ID alias checks in registered contact,
  note and task mutation hooks. Use the shared binder before `recordId`/`project`
  and before any receipt. Obtain the bound schema from the exact held request
  supplied by dispatch: retrieve it with `returnedIdentitySchemaFor(frozen)`
  inside both existing hooks, then call `bindReturnedIdentities`. Never use a
  last-prepared global or reconstructed arguments.
  Retain operation-specific payload/confirmation checks. Cover nested parent,
  custom-field and assignee identities, creates/upserts, no-ID responses and
  exact contact follower sets. Refuse hooks invoked without bound mutation
  context. Use the same gate for reconciliation read results where applicable.
- **hlf2:** do the same for registered opportunity/pipeline/status/follower hooks.
  Remove named alias checks; bind contact, pipeline, stage, assignee and location
  roles from approved bytes. Confirm exact follower sets, existing/new pipeline
  stage rules, and upsert `new` semantics. Never allow identity disagreement in
  a field merely because projection discards it.
- **hlc2:** route **every approved write**, including policy-approved writes,
  through `runApprovedWrite` with the stable approval ID and request digest from
  the verified durable approval intent. Do this before entering a new dispatch:
  terminal replay must not call `beginDispatch` on an already-terminal action.
  Only inside its first-dispatch callback call `beginDispatch`, prepare the
  bound schema from its retained held request, and send exactly that held once.
  Bind the raw response before family `recordId`/`project`, then validate/project
  under the release/authority guard. Pending replay obtains safe read targets
  from durable action metadata and the existing recheck path; inability to
  recover enough context yields conflict, never reconstructed write bytes.
  Map binder conflict to journal `identity_conflict` and existing action
  `outcome_unknown` (withhold); map negative confirmation to journal
  `negative_confirmation` and action `not_applied`. Do not add an ActionPhase.
  Persist safe applied result before settling applied/releasing it. Map ambiguous
  read reconciliation to `unconfirmed`, authority failure to `authority_changed`,
  preserve stale, and never resend pending. Keep approval records after action
  cleanup. On terminal replay, verify current release authority and return the
  stored result; never call send again. Test these paths through the real
  production dispatcher in isolated fixtures. The shared tests do not prove
  production wiring that remains in the C2/family lanes.

## Verification

Tests generate every write schema's identity keys plus review examples at depths
1–3 as object siblings and inside arrays. Positive approved/new/pass-through,
role separation, stage creation, deep traversal, negative confirmations and
exact followers are covered. Removing only array recursion must make that table
fail. Replay tests cover durable pending-before-send, repeated approvals,
concurrency, corrupt records, write/read failure, and an accepted fake-provider
write followed by a crash and a real reconcile GET with no second POST.
F0/F0.1 preservation and the separate F0.2 snapshot are checked, with both tsc
configs and CI classification. All test runs use isolated containers; fixture
launch/doctor proves isolation/startup only, not unimplemented family adoption.
