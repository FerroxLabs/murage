## Why r4 cuts scope

After three in-lane Astra rounds, seven of r3's nine open findings were the third appearance of the same clusters (r2 → conv r2 → conv r3). Each cluster came from a part of the design that has to agree with another part across a process boundary or a disk boundary. r4 removes those parts rather than adding guards:

| Recurring cluster (Astra conv3 #) | Root | r4 cut |
| --- | --- | --- |
| Lease vs narrowing, REPLACE, relink (#2, #5, #8) | the value left main in a *lease*; the server dispatched later, so every narrowing raced a lease in another process | **No leases.** Main makes the HTTPS request itself. Check, value read, dispatch, abort, narrowing and REPLACE all run on main's one event loop (4.4, D13) |
| Shared credential writer (#3, #9) | Vault ops shared `credentials.bin`'s writer, so Vault recovery had to reason about sign-in drafts and sibling saves | **Own file, own writer.** `userData/secrets/vault.bin`, written only by the Vault (D1, 5.3). The shared writer is untouched; its existing bug moves to V4 |
| Narrowing journal durability (#4) | a second durable file had to be written at the moment of a narrowing, and that write can fail | **No journal.** A marker is *armed at boot* while the disk accepts writes. A lost narrowing needs no further write to stay fail-closed (5.4) |
| Chat holds (#5) | an in-memory value with its own lifetime, display and fence | **Cut to V2.** A card either keeps the value in the Vault or grants a saved item |
| Duplicate POST after remount (#6) | identity built from engine-chosen request ids and proxy instances | **Identity from the call itself**, held by main (D23) |
| Redirect carrying the value (#7) | following redirects | **No redirect is ever followed** (4.4 step 5) |
| Full-access bearer after unpause (#1) | a turn claim had no notion of when it was issued relative to the pause | **Exposure generation in the claim** (D25) |

## 0. PURPOSE and USER PROMISES

PURPOSE: the owner gives an API key or token once, on a bot's secure card or on Settings → Vault, and the bots the owner chose can use it later in web requests Murage makes for them to the sites the owner allowed. The value never reaches a model, a file other than the sealed Vault file, a log or another program.

USER PROMISES (each tested in 9; what Murage cannot enforce is in 1.1):
- **P1 Save once.** A saved value is used again, with no new card, when a bot it is granted to asks for it by name for a site the item allows.
- **P2 Only chosen bots, only chosen sites.** Murage sends an item only for a bot listed on it, only to an origin listed on it (exact scheme, host, port), only in the slot listed on it, and only for a turn that no other program could have impersonated (D25). A bot that is not listed gets a card for the owner to decide, never the value.
- **P3 Never in the model, a file, a log or another program.** No Vault value is ever in a prompt, a tool result, a transcript, an event, a log line, the server process (values go renderer → preload IPC → main, D28; the server never holds one), any process's argv or environment, any child process, any file other than `vault.bin`, config.json, a backup, telemetry, feedback or a crash report. The response the bot sees has every pinned form of the value masked (F9); a body Murage cannot scan returns only its size, never a digest or other function of its bytes (4.4 step 6). The pinned site receives the value: the owner's choice (R2).
- **P4 Honest "saved".** "Kept in the Vault" is shown only after a full durable write of `vault.bin` that contains the op. Before that the card says "Saving…", or "Not confirmed yet" after an ambiguous write. A save that failed says "Not kept: <reason>. Ask again." "Not kept" is said only when the file is known not to hold the op, and an op told "Not kept" (or "Not removed") is never written later (V7).
- **P5 Never silently weak, never silently lost.** The Vault is READY only where its file is sealed by the OS store (macOS Keychain, Windows DPAPI, Linux libsecret/KWallet). Linux `basic_text`, headless servers and Cloud homes keep it LOCKED in part 1, with the reason. A Vault file that cannot be read is never replaced or emptied.
- **P6 Owner control.** The owner sees every item (name, bots, sites, slot kind, last used; never the value), changes bots and sites, replaces the value, deletes it. A revoke, site removal or delete takes effect at once for every request that has not started and aborts every request in flight that holds the item. A saved-secret write stalled on a slow disk never delays a revoke (D29). If Murage closes or the computer loses power before it could save that change, saved secrets stay paused after it reopens until the owner checks the Vault page and presses Resume.

## 1. Threat model

Assets: Vault values; each item's bots, sites and slot.

| Actor | Can | Must not be able to |
| --- | --- | --- |
| Owner (renderer, owner routes) | everything in P6 | read a value back (no route returns one) |
| A bot / model, incl. one steered by prompt injection | ask by name with a proposed site and slot; call `vault_fetch` for a granted item | get an item not granted to it; send it to a site or slot not pinned; receive a value in any result, error or prompt; reach any origin other than the pinned ones; make Murage follow a redirect |
| Another bot (not on the item) | everything a bot can | get the value or a signal about it (mask counts) through any Murage tool, card or route |
| Engine children, the server process | what they have today | receive a Vault value (the server never does: values go from the owner's desktop renderer straight to main, D28) |
| Disk thief / backup reader / old-version backup | read userData and backups | find a value (only `secrets/vault.bin`, sealed, excluded from every backup in 1.0.20 and 1.0.21, 7) |
| A pinned site | receive the value in the pinned slot | receive another item, or a value outside a request a granted bot made |

### 1.1 Residuals (Q1 asks the product owner for a NEW acknowledgement)
- **R1 Same OS user.** A program running as the owner's OS user (a Full-access bot's command, or other software) can, on Windows and Linux, ask the OS store for the key that seals `vault.bin` (as for `credentials.bin` today), and on Windows read Murage main's memory. Such a program can also read a turn's bearer file (`server/drivers/claude.ts:4930-4940`) and act as that bot on internal routes; D25 pauses the Vault while any bot can do that and voids every claim that existed during the pause. **Demoting a bot does not undo programs it already started while it had Full access**: such a program is "other software running as you". The Vault page says: "Bots with Full access run as you and could read Murage's saved keys, including these. Lowering a bot's access does not stop programs it already started. Give Full access only to bots you trust." `docs/terms-acceptance.md:13` covers only the terms record, so this is a new acknowledgement.
- **R2 The pinned site.** The site receives the value. A site that echoes it in a form outside F9 (including a compressed reply whose size changes with bot-chosen text next to the value), or a granted bot that sends its own context to that site, acts within the owner's grant. The card says: "<bot> will be able to send requests to <origin> with this. Only allow sites you trust with it."

Out of model: malware with debugger access to Electron main; a compromised OS keychain; a compromised CA for the pinned site.

## 4. Flows

### 4.1 Save from a card
1. Bot calls `request_credential({credential_id: "custom:<label>", reason, use: {origin, slot}})`. `origin` = `https://host[:port]` (`validateHost`; DNS names and public IP literals; no path, no userinfo). `slot` ∈ `bearer` | `header:<Name>` (`^[A-Za-z][A-Za-z0-9-]{1,63}$`, not reserved, 4.4) | `basic:<user>` | `query:<param>` (`^[A-Za-z0-9_.-]{1,64}$`). `nameKey = vaultNameKey(label)` (NFKC, lowercase, runs of non-alnum → `-`, trimmed).
2. Store not READY or flag off → no card: `Secrets can't be saved here: <reason line>.` No limits turn → no card: `Saved secrets are paused while <bot> has Full access. Lower its access, then save it in Settings → Vault and allow <bot> and <origin> there.` (Fable r4 M3).
3. A live item with that nameKey granted to this bot, listing `origin`, with this slot → no card: `"<name>" is saved for <origin>. Use vault_fetch with name "<name>".`
4. Otherwise a card. Header "**<bot> wrote this name and reason**", label, reason. Site line: "Murage will send it only to **<registrable domain>** (<full origin>), as <slot words>." (registrable domain emphasised, Fable r3 M6). The owner may edit the origin (validated again). Single-line password input. Choice "Keep in the Vault for <bot>". If a live item with that nameKey exists and its slot equals the requested slot, the card also offers GRANT: "Let <bot> use the saved '<name>'", stating the item's whole scope (every origin, slot, every granted bot); when the request adds an origin, a separate line: "**Adds a new site:** <origin>, for every bot on this item." A different slot → no GRANT; typing a value creates a new item `<label> (<bot name>)`; so does typing a value when the same name and slot exist (KEEP never edits an existing item) (Fable r4 M8). A card never replaces a value. The card records the item `generation` it displayed; GRANT carries it as `baseGeneration` (Astra conv4b #4).
5. Settlement: one store transaction does the CAS `OPEN → SETTLED(keep|grant)` on the card message and writes the op record `{settlementId, opId, kind, state: PENDING}`; second submit or submit after dismiss → 409. Only owner routes settle; in a group room the item goes to the asking bot only. After the commit the server returns `{opId, valueToken}` to the renderer and posts the op (no value) to main; the renderer sends the value to main by preload IPC (D28).
6. Ops: keep → `SAVE {item: {name, nameKey, value, bots:[bot], origins:[origin], slot}}`; grant → `GRANT {itemId, botId, origin?, baseGeneration}`.
7. Card outcome line: KEPT "Kept in the Vault for <bot>"; NOT_KEPT "Not kept: <reason>. Ask again." (SAVE) or "Not allowed: <reason>" (GRANT); before the outcome "Saving…".
8. Continuation (existing resume path), only after the outcome: KEPT → `Secret "<name>" is ready for <origin>. Use vault_fetch with name "<name>".`; NOT_KEPT → `The owner answered, but it could not be saved: <reason>. Ask again later.`; DISMISSED → `The owner declined.` Never a value.

### 4.2 Settings → Vault page
Items: name, bots, sites, slot kind, last used, "in use" while a request holds it. Actions: Add (name, value, sites, slot, bots), Replace value, Change bots, Change sites, Delete. Write-only value field; the value goes page → preload IPC → main (D28); the server route carries only metadata. Store line: READY; LOCKED(keyring | headless | cloud | disabled | store-unavailable | full-access | review | loading); BROKEN ("The Vault could not be opened. Nothing was changed."). `full-access` names the bots causing it; an engine/OS pair not yet qualified has its own line: "Saved secrets are paused: <engine> on this computer has not passed the sandbox check yet." (Fable r4 M3). `review`: "Murage closed before it could confirm a change. Check who can use your saved secrets, then press Resume." with the Resume button. Unsaved narrowing: "Removed. Not saved yet; Murage keeps trying. If Murage closes first, saved secrets stay paused until you check them here." with Retry. Pending ops: "Saving…". R1 line. UX per `designs/MURAGE-UX-BAR.md`, strings via the inventory. While LOCKED(review) the owner can still edit and delete.

### 4.3 "Use a saved one"
Custom cards only (D8). Picking a saved item = GRANT (4.1 step 4).

### 4.4 `vault_fetch` (the only delivery, executed in main)
Tool on the agents proxy beside `request_credential`:
`vault_fetch({ name, url, method?: "GET"|"HEAD"|"POST"|"PUT"|"PATCH"|"DELETE", headers?: {[k]: string}, body?: string, timeout_s?: number, repeat?: integer })`. The description says: an identical call in the same turn returns the first call's result; set `repeat` to send it again.
- `url`: absolute `https:`, ≤ 8 KiB, no userinfo, no fragment; origin must equal one of the item's origins; for a `query:<param>` slot the URL must not contain `<param>`.
- `headers`: names `^[A-Za-z0-9-]{1,64}$`, values without CR/LF, ≤ 16 KiB. Reserved (refused): `authorization`, `proxy-*`, `cookie`, `host`, `content-length`, `transfer-encoding`, `connection`, `te`, `upgrade`, `expect`, `accept-encoding`, `range`, `if-range`, and the item's pinned header name.
- `body` ≤ 1 MiB text. `timeout_s` ≤ 60, default 30.

Steps:
1. **Ingress (server, one synchronous block):** `VAULT_ENABLED`; the bearer resolves to an active claim (`requireActiveInternal`, `server/index.ts:30578`); **exposure gate D25**; argument checks above; compute `invocationKey` (D23); post `vault-fetch {epoch, botId, threadId, turnGen, invocationKey, name, url, method, headers, body, timeout_s}` to main and await the reply (backstop 120 s → fixed string `Outcome unknown: Murage lost the reply. Check before repeating it.`; the proxy waits 250 s).
2. **Join (main, synchronous):** `invocationKey` in the session map → wait for it or return its stored result. Otherwise insert RESERVED.
3. **Check and dispatch (main, one synchronous step, D13):** epoch is the running child's; store READY; main's `exposure.active` false; `turnGen` not ended or Stopped (`deadTurns`); `name` resolves in `effective` (minus `blocks`, D31) to exactly one item granted to `botId` (two → refused naming both, Fable r4 M8), with `url`'s origin listed, not `replacing`; then read the value, build the request (value only in the pinned slot; model headers after the reserved check; `accept-encoding: identity` set by Murage), create the Node `https.request` object, register `inflight[reqId] = {itemId, botId, turnGen, epoch, abort}` and mark the key DISPATCHED. Any failure → fixed refusal string, nothing sent, and the key is **deleted** (not DONE): a refusal is never stored, so after the owner grants or presses Resume the identical call is checked again (Fable r4 M2). DONE is kept only for calls that were dispatched (including timeout, reset and stopped).
4. **Transport:** Node `https` (not Electron `net`, which applies the system proxy); certificate verification on; no proxy; a `lookup` hook that rejects any address where `isPublicAddress` is false, on every connection; keep-alive off.
5. **Redirects:** never followed (D26).
6. **Response:** status number only; `content-type` reduced to bare `type/subtype` matching `^[a-z0-9.+-]{1,64}/[a-z0-9.+-]{1,64}$`; `content-length` number; no other header except a scrubbed `Location` (D26). Body is text only if: the type is `text/*`, `application/json`, `application/xml`, `application/*+json`, `application/*+xml` or `application/x-www-form-urlencoded`; **and** `content-encoding` is absent or `identity`; **and** the charset is absent, `utf-8`, `us-ascii` or `iso-8859-1`. Text bytes go through the streaming matcher (F9) with carry-over, **then** are decoded, **then** capped at 256 KiB (end dropped with a marker). Because values are printable ASCII and the three charsets are ASCII-compatible, byte matching equals text matching (Fable r3 M1). A `206` or any `content-range` response is never text. Anything else is **opaque**: its bytes are counted and discarded as they arrive, never hashed, scanned or kept, and the result carries only `{size}` (bytes received); reading stops at 8 MiB with `{size: 8388608, truncated: true}` and the request is aborted. No digest, prefix or other function of opaque bytes ever leaves main (Astra r4d #4, Fable r4 M7): Murage would compute it, so R2 does not cover it, and an echoed short value is identified only by length, which the bot already knows. Every returned string (media type, `Location`) passes the matcher.
7. **Abort:** a narrowing or REPLACE on the item, `vault-exposure {active: true}`, `vault-turn-end {turnGen}` (Stop confirmed or turn end), server exit (E1), the timeout, or app quit → `abort()` (bytes already on the wire cannot be recalled; the result says "stopped").
8. **Result:** `{status, contentType, location?, body | {size}, masked: N, truncated?}`; `masked` counts this call's value only. Errors are fixed strings by class (DNS, TLS, refused address, timeout, reset, too large, stopped), never a library message. The key becomes DONE(result); `inflight` entry removed; reply to the server. Main updates `lastUsedAt` in the pushed index.
9. **Log:** server: bot, item name, origin, method, status, ms. Main: nothing per call. Never path, query, headers or body.

The map entries of a turn are dropped 10 minutes after `vault-turn-end`; a later call on that turn is refused at ingress anyway (claim inactive). The map is bounded at 4096 DONE entries of ended turns (oldest first); RESERVED and DISPATCHED entries are never evicted. Stored results of live turns are bounded at 8 MiB per turn (each ≤ 256 KiB + metadata); past that the oldest DONE result of that turn keeps only its status line, and a redelivery of it gets `Already sent in this turn (status <n>); the reply was too large to keep.` Never re-sent.

### 4.5 Bot deleted
Before `store.deleteBot` commits, post REVOKE_BOT(botId): enters `overlay`, aborts that bot's in-flight fetches, queued write. The delete does not wait for the write (D19).

### 4.6 Rollback
`VAULT_ENABLED=false` (D18): `secrets/` untouched, a fixed build finds every item.

### 5.3 The Vault writer (own file, own queue, blocking steps on the worker)
One serialized queue in main. A write = main computes `next` and `seal(next)`, then posts the sealed bytes to the persistence worker (D29), which runs `writeFileDurable(<profileDir>/secrets/vault.bin)` (temp `vault.bin.<pid>.tmp`, fsync, rename, then POSIX directory fsync or the Windows reopen-flush, `electron/durable-write.mjs:9-27`) and replies ok, or the error and whether the rename was reached. Main's event loop is free for the whole write: narrowings, REPLACE marks, exposure, Stop, turn end, fetch dispatch and the provider-key writer all run meanwhile (Astra r4d #2). When the write fails, or the worker dies with it in flight:
0. The worker unlinks the temp if it still exists (best effort; boot sweeps it otherwise, 5.4 step 4).
1. `disk = readBack()`: the worker reads the raw bytes; main decrypts and parses. ENOENT is reported as such (D32).
2. `disk` equals `doc`, **including ENOENT while `docOrigin = ABSENT`** (an unpublished first write, Astra r4d #5): the job's widening is NOT_KEPT; every narrowing in `snap` stays PENDING in `overlay` (D31); store stays READY (Fable r3 M2); writes resume.
3. `disk` equals `next`: re-persist `next` with the full durable path. Ok → `doc = next`, `docOrigin = FILE`, KEPT (widening and every narrowing in `snap`). Throws → **UNCONFIRMED**: `uncertain = {next, opIds}`; the widening is not usable (fetch checks `effective`, built on `doc`), the card says "Not confirmed yet" (Astra conv4 #3); the narrowings in `snap` stay in `overlay`, in effect, PENDING.
4. Read fails, ENOENT while `docOrigin = FILE`, or `disk` is neither `doc` nor `next`: **UNCONFIRMED** with `uncertain = {next, opIds}`, and **no further write of any kind** until reconciled (Astra conv4 #4).
Reconciliation (before every later job, on the page Retry, and by a 60 s retry job, never by a timer outcome), through the worker: read back; equals `uncertain.next` → re-persist it durably → `doc = next`, `docOrigin = FILE`, every op in `opIds` KEPT; equals `doc` (incl. ENOENT with `docOrigin = ABSENT`) → widenings in `opIds` NOT_KEPT, **narrowings in `opIds` back to PENDING in `overlay`** (never NOT_KEPT, D31), writes resume; unreadable after the app had read it this session, ENOENT with `docOrigin = FILE`, or any other document → **BROKEN** (D5: fetch refused, no write, bytes kept, page line; narrowings stay in effect in memory, PENDING, and the armed marker keeps the next boot in review). While `uncertain`: widenings NOT_KEPT(store-unconfirmed), narrowings enter `overlay` and wait, fetches answer from `effective` (which never includes the unconfirmed widening).
A failure sets `writeFailedSinceLastOk`, so the marker stays armed at quit (D27). The next successful write persists `apply(overlay, doc)` plus its own op, so the file returns to exactly what main holds.
A worker that does not answer: its job stays in flight (no timer outcome); later jobs wait behind it; narrowings and fetch checks keep running on main; quit keeps the marker (Q1).

No other code writes `secrets/`. Nothing outside the Vault ever waits on this queue (Astra conv3 #9 by construction), and nothing on main's event loop waits on the worker (D29).

### 5.4 Boot (main)
0. Vault boot runs after `requestSingleInstanceLock` (`electron/main.mjs:1288`) and after `configureRestoredDesktopConnections` (`:1765-1771`), so a second launch never sweeps the running instance's temp and `profileDir`/`vaultRoot` are final (Fable r4 M9). Every file step below runs on the persistence worker (D29).
1. Store state from the platform (D6) and `VAULT_ENABLED`. `profileDir = dirname(CREDENTIALS_FILE)`, `vaultRoot` per D30.
2. **Marker first (D27):** `secrets/vault.open` exists → `review = true`, `markerOwned = false`, one in-app notice "Saved secrets are paused. Check them in Settings → Vault." (Fable r3 M4). This is decided before any step below can fail.
3. Read `vault.bin`: confirmed absence (ENOENT on `secrets/` or the file) → empty `doc`, `docOrigin = ABSENT` (D32), no directory is touched; any other read error → LOCKED(store-unavailable) with Retry, `docOrigin = FILE` (never treated as empty); decrypt/parse/schema failure → BROKEN (D5); ok → `doc`, `docOrigin = FILE`.
4. Sweep (only when `secrets/` exists): unlink every `secrets/vault.bin.*.tmp`, then fsync `secrets/`. Failure → LOCKED(store-unavailable) and **all Vault writes held** (narrowings stay in memory) until a retry of the sweep succeeds (Astra conv4 #8, conv4b #5).
5. Re-persist (only when `vault.bin` exists and is not BROKEN): write `doc` with the full durable path, so every receipt the boot read sees is durable and M4's KEPT-by-receipt is true (Astra conv4 #3); failure → LOCKED(store-unavailable) with Retry.
6. Marker arm (when `vault.bin` exists and `review` is false): create `vault.open` (`O_CREAT|O_EXCL`, fsync file, fsync `secrets/`; win32: FlushFileBuffers on the marker handle), `markerArmed = markerOwned = true`; failure → LOCKED(store-unavailable), retried with the page Retry and before every narrowing (M2). When `review` is true the existing marker counts as armed (`markerArmed = true`, `markerOwned = false`).
7. READY, or LOCKED(review) while `review`.
8. Each server fork: `vault-hello` → index; `vault-op-status` for every non-terminal op record.

First write of each session (new Vault, a restored profile whose directories do not exist yet, `server/installation-restore-preparation.ts:249` writes only the profile marker, or a retry after a failed preparation): **preparation** = create each missing directory down to `secrets/`, then fsync (POSIX) **every directory on the chain from `secrets/` up to and including `vaultRoot` (D30)**, whether this session created it or not, so a retry after a failed parent fsync, also after a restart, re-establishes the barrier (Astra conv4c #3). Default profile: `secrets/`, userData. Restored profile: `secrets/`, `connection-profiles/<id>`, `connection-profiles`, the selected installation's data directory; userData is not on that chain and is never its endpoint (Astra r4d #3). `vaultRoot` itself pre-exists (userData holds the default `credentials.bin`; the data directory holds the data-dir lease and `restored-connections.json`), so its own entry is not part of the chain. Then the marker (step 6 sequence), which sets `markerArmed = markerOwned = true` (Fable r4 M6: a clean quit after the first-ever save then removes it). `dirsDurable = true` only when all succeed. A preparation failure → the widening NOT_KEPT(store-unavailable), nothing written; a narrowing needs no preparation (with no `vault.bin` there is nothing it can remove: it is KEPT at once without a write). Once the document write starts, 5.3 alone decides: a rename followed by failed flushes is UNCONFIRMED, never NOT_KEPT (Astra conv4c #2); a failure before the rename on a profile with `docOrigin = ABSENT` reads back ENOENT, which equals the empty `doc` (D32), so the save is NOT_KEPT and the next SAVE in the same session runs normally (Astra r4d #5).

**Windows barriers (Astra conv4c #4, r4d #6).** Windows has no directory fsync (`server/atomic.ts:81,95`, `electron/durable-write.mjs:18-22`). On win32 every "fsync a directory" step above is skipped; the marker is created with `O_CREAT|O_EXCL`, written and flushed with FlushFileBuffers on its own handle (the same rule the existing writer relies on for a renamed file: NTFS commits the file's entry with its flush); the sweep and the marker removal are plain unlinks. A Windows boot therefore never fails on a directory barrier. **Power-loss model, stated so it can be tested (W16i-win):** after a power loss, a file's bytes survive only up to its last successful flush, and a created or renamed entry survives only if a later flush of that file (win32) or of its parent directory (POSIX) succeeded. The marker is the only thing V4 needs to survive, and it is flushed at arm time, before any narrowing can be accepted (M2).

Why the marker closes the lost-narrowing case: it is created while the disk takes writes (boot), so a later narrowing needs no write to stay fail-closed. If the narrowing's write fails or stalls (full disk, copy-on-write snapshot, a hung flush on the worker) and Murage then crashes, quits or loses power, the marker is still there (it was flushed at arm time); quit removes it only when this session owns it and everything is saved. A review is latched: quitting from it, or from any failed boot, keeps the marker, so the next boot is in review again. A crash with nothing unsaved also leaves it: that costs one Resume press and is stated on the page.

**One terminal path:** every op ends KEPT or NOT_KEPT(reason) at the end of its own job (M3), after reconciliation of an UNCONFIRMED write (5.3), when a later write that includes a PENDING narrowing succeeds (M3), at acceptance for a rejected narrowing (M2, never in `overlay`), or by receipt or its absence after a restart (M4). A narrowing in `overlay` reaches only KEPT (D31). PENDING and UNCONFIRMED are not terminal and are never shown as failure. No timer creates an outcome (sole exception: D28's 60 s value join).
Invariants: **V1** "kept" only when a document containing the op completed a full durable write. **V2** no fetch is checked against anything wider than `effective`; a narrowed target is usable again only after a later widening on it is KEPT. **V3** `vault.bin` is never written while BROKEN. **V4** after an unsaved narrowing, no fetch runs after a restart until the owner presses Resume. **V6** an op is reported KEPT only from a durable write of this session or a receipt in a document re-persisted at boot; NOT_KEPT only when the file is known not to hold it. **V5** no Vault value is ever in the server process or the persistence worker (sealed bytes only, D29). **V7** a narrowing told NOT_KEPT is in no write set and no `overlay`, so no later write can commit it; a narrowing in `overlay` is never told NOT_KEPT (D31). **V8** no blocking file call runs on main's event loop for the Vault (D29). **V9** the first-write fsync chain ends at `vaultRoot` of the selected profile (D30).

## 7. Migration and compatibility

- From Murage today: nothing to migrate. `credentials.bin` is never read or written by the Vault.
- Inventory: `secrets` and `connection-profiles` stay `excluded(CREDENTIAL)` (already in 1.0.20 and 1.0.21); the `secrets` comment names VAULT-M7 as owner of `secrets/vault.bin`, `secrets/vault.open` and their temps.

- Restore: `secrets/` never travels in a backup; a restored computer starts with an empty Vault. Same-machine restore selects a fresh connection profile (`restored-connections.mjs`), and the Vault follows it, so the restored installation starts empty even though bot ids match, and the original's Vault is untouched.
