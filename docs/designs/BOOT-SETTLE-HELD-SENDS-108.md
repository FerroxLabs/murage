## 1. Today

The 100k case is expiry cleanup, not 100k deliveries. It inserts owner-origin rows with `phase='started'`, `started_at=NULL` and ancient `submitted_at=1`, replaces `patchMessage` with a counting callback, and expects zero turns. Its comment reports 195 s under FULL, approximately 1.7 ms per commit sync, and 14 s without those syncs; the checked-in test uses `synchronous=OFF`. These are historical fixture observations, not results from this revision (`server/pm-sends-102-r24.test.ts:262-283`).

Database open sets WAL and FULL. Each held release uses `Store.patchMessage` to couple its row change, control and registration. Without a surrounding transaction, message updates commit individually; nested transactions use savepoints. This provides a narrow opportunity to batch expiry/control cleanup without batching receipt persistence (`server/database.ts:280-289`, `server/database.ts:459-487`, `server/delegations.ts:1678-1690`, `server/message-db.ts:1095-1105`).

Current boot sequence:

1. Owner-record migration holds admission and retries automatically with a 1 s delay doubling to a 60 s cap. Its completion listener runs synchronously. Server `withSource` also invokes settle synchronously, so taking the reconciliation hold before the first await does not introduce a migration-to-settle gate window (`server/pending-delegations-schema.ts:291-346`, `server/io-budget.ts:144-148`, `server/index.ts:13824-13827`, `server/index.ts:13854-13856`).
2. Settle takes a hold, yields and waits for `startupWritesReady`. Even empty boot does this. First health releases the wait; the fallback is 5 s with a 60 s total bound when the loop remains busy (`server/delegations.ts:1594-1601`, `server/after-listen.ts:18-48`).
3. It scans STARTED, HELD, SHARED, ORPHANS, then OWED. Started rows use `(started_at,rowid)`, held rows `id`, orphan controls `message_id`; shared reset uses rowid ranges up to a captured maximum. Started/held/orphan pages are 100, shared ranges 500, and OWED currently filters the receipt array and runs unpaged (`server/delegations.ts:228-257`, `server/delegations.ts:1562-1609`, `server/delegations.ts:1641-1660`, `server/delegations.ts:1731-1742`).
4. `finally` releases the hold even on rejection. The server catches that rejection before a success continuation which both interrupts unresolved event tickets and drains. Retaining a hold on failure therefore requires changing both continuations. The separate `bootSettled` timeout is not evidence that hand-off admission can open (`server/delegations.ts:1610`, `server/index.ts:13838-13847`, `server/after-listen.ts:62-75`).
5. The room boot sweep runs separately during server initialization, before the asynchronous HELD pass. It excludes a request partnered with a non-held pending row; an already-held partner can be ended as `unknown`. A crash after `saveReceipts` but before `settleReceipted` commits therefore leaves a saved receipt whose partner the next boot ends first; `completeRequest` will not change that terminal outcome. Retrying settle does not rerun the sweep (`server/delegations.ts:483-489`, `server/delegations.ts:1599-1606`, `server/index.ts:16223`, `server/room-requests.ts:1339-1352`, `server/room-requests.ts:767-770`).

| Existing record | Decision to preserve |
| --- | --- |
| Started, never submitted | Reset to fresh and requeue its paired request; reuse an existing prompt. Repeated cut-short starts become owner-held (`server/delegations.ts:1486-1499`). |
| Accepted, or submitted with provider evidence | Receipt as interrupted, preserving any existing receipt; no automatic repeat of provider execution (`server/delegations.ts:1467-1482`). |
| Submitted without evidence | Change to held; the notice pass records the outcome and owner controls. Eligible holds older than 30 days expire without sending (`server/delegations.ts:1481-1484`, `server/delegations.ts:1696-1719`). |
| Stopped owner/channel sends | Separate recovery and explicit resend-token rules; boot hand-off reconciliation does not release them (`server/send-store.ts:538-547`, `server/send-store.ts:791-802`). |
| Pending work from a restored backup | Pending hand-offs are quarantined and removed during restore preparation. Restore-held outputs/results retain their explicit owner-action release rules (`server/installation-restore-preparation.ts:380-392`, `server/restore-fence.ts:257-265`, `server/restore-fence.ts:276-296`). |

**Why blanket batching is removed.** `recordDelegationReceipt` replaces the in-memory array, writes/fsyncs the JSON file, then calls `settleReceipted`. That call can complete a room/shared partner and queue an asker wake. SQL rollback does not undo the receipt file or array; transaction rollback discards the wake. A held row survives `removeStarted`, and `noticeHeldOne` skips receipt recording when the receipt already exists. Consequently, wrapping multiple held notices in one transaction creates the lost-settlement path identified by Grok (`server/delegations.ts:388-396`, `server/delegations.ts:483-489`, `server/delegations.ts:598-633`, `server/delegations.ts:255`, `server/delegations.ts:1718`, `server/index.ts:14583-14606`, `server/tx-scope.ts:15-24`).

For N eligible SQL-only releases and P=100, the sync component changes from approximately `N*F` to `ceil(N/P)*F`. At the fixture's reported F, 100k releases imply about 170 s versus 1.7 s of commit syncs, excluding row work and all other I/O. This is a model for the eligible expiry path only. Receipt-file rewrites still fsync independently and are not accelerated by this design (`server/pm-sends-102-r24.test.ts:264-266`, `server/atomic.ts:85-97`).

## 2. Boot-settle state machine

Use one process-local completion promise, one owned reconciliation hold and at most one scheduled retry. Keep the five existing scans and their cursors. No exported phase enum, UI status machine, durable journal or separate replay queue.

Before starting a job, check migration pending. If pending, leave admission to its existing gate and return without running any completion continuation; its existing listener will call the entry point again. Otherwise acquire the reconciliation hold synchronously. Duplicate boot/migration calls join the same job; after it completes they do not run ticket cleanup or boot drain again (`server/pending-delegations-schema.ts:297-308`, `server/index.ts:13854-13856`).

| Job condition | Action |
| --- | --- |
| Running | Wait for startup writes once, then walk STARTED, HELD, SHARED, ORPHANS and OWED. Each bounded unit ends with a real event-loop yield. |
| Waiting to retry | Retain the same hold and uncommitted cursor. Schedule one automatic retry under section 4.9. The completion promise remains pending. |
| Complete | After the final unit, its commit effects and final yield, release this job's hold once and resolve. Only the success continuation runs `interruptUnresolvedEventTimeoutsOnce()` and then the existing boot drain. Other holds still apply. |

Cursors advance after a SQL batch commits or an individual row has been examined and either completed or explicitly deferred. A deferred started/held row remains non-runnable; it is not counted as a successful settlement. Restart discards cursors and begins from the indexed predicates again. Deleted rows disappear; reset rows no longer match STARTED; stable held-line IDs avoid duplicate owner lines (`server/delegations.ts:232`, `server/delegations.ts:1484-1498`, `server/delegations.ts:1663-1671`).

A receipt file is recovery evidence, never proof that its SQL settlement committed. Receipt-first persistence and owed-reply retention remain intact. On restart, the room sweep must defer every request with a pending hand-off row, including a held row, to hand-off reconciliation. The HELD pass re-enters settlement from the current saved receipt; it cannot rely on the process-local `stranded` set surviving a crash. Existing `resettleStranded` still owns failed individual settlements within one process; a failing row must not prevent later rows from being examined (`server/room-requests.ts:1341-1352`, `server/delegations.ts:421-444`, `server/delegations.ts:568-583`, `server/delegations.ts:598-633`, `server/pm-sends-102-r29.test.ts:175-188`).

## 3. Proposed change and delivery guarantees

**Bounded units.** P=100 remains the maximum number of root candidates examined between yields. STARTED processes one row per unit because its helper may persist a receipt. HELD either processes a contiguous SQL-only expiry prefix of at most P rows or one individual row. ORPHANS processes at most P registrations. SHARED uses rowid ranges of P instead of 500. OWED examines at most P entries but attempts at most one receipt settlement per unit. End every unit, including a short final unit and every phase transition, with `setImmediate`; never await inside a transaction. This caps grouped SQL and receipt-bearing work separately (`server/delegations.ts:1563`, `server/delegations.ts:1605-1609`, `server/delegations.ts:1651-1660`, `server/database.ts:459-485`).

**Batch only two SQL-only paths:**

1. HELD expiry: require a currently held owner-origin row, non-null submission older than the existing 30-day cutoff, no paired request, and `findDelegationReceipt(id) === null`. This intentionally narrow predicate covers the cited 100k fixture. Room/shared rows and any retained receipt, including owed or held replies, use individual processing. Do not bypass the existing cancellation-before-expiry decision (`server/delegations.ts:1697-1706`, `server/delegations.ts:655-659`, `server/pm-sends-102-r24.test.ts:269-271`).
2. ORPHANS: clear a registered control only when the current row is absent or no longer held, using the existing `releaseHeld(..., () => false)` path (`server/delegations.ts:1733-1740`).

Read candidates in the existing key order and re-read eligibility inside the transaction. Consume only the next eligible prefix; never collect later eligible rows past an individual row. If the first candidate needs individual handling, process it outside any page transaction. If eligibility changes inside the transaction, stop before that row, commit the earlier prefix and reconsider that key after yielding. This preserves ordering without a second work list.

Enclose each nonempty SQL-only prefix in `transaction(..., {op: ...})`. Use the existing row transactions as savepoints; do not add another savepoint layer. Advance counts/cursor only after the outer commit. A row-local exception leaves its row/registration for a later pass; errors matched by the proposed `isBootSettleOperationalError` in section 4.9 must escape row catches and retry the unit. Outer BEGIN/COMMIT failures also retry the unit. Keep row-local catches outside their row transaction and inside the outer transaction callback, so a deterministic row error is not mistaken for a COMMIT failure. Store events wait for the outer commit and rollback invalidates affected cached threads (`server/database.ts:459-487`, `server/message-db.ts:1095-1105`, `server/store.ts:2099-2101`, `server/store.ts:2644-2649`).

**Keep receipt operations out of outer boot transactions.** Do not enclose STARTED decisions, held notices, cancellation receipts or OWED replay in the SQL batch. `removeHeldRow` can call `deliverOwedBeforeRemoval`; the strict expiry eligibility check is therefore essential. A newly discovered receipt sends that candidate to individual handling. Qualify that no receipt writer/listener executes under the new outer transaction (`server/delegations.ts:353-357`, `server/delegations.ts:1690`, `server/delegations.ts:1514-1533`).

**Saved-receipt recovery, without another durable state.** In `reconcileRoomRequestsAtBoot`, remove the held-row exception from the partner exclusion. When `pending_delegations` exists, use `AND NOT EXISTS (SELECT 1 FROM pending_delegations p WHERE p.id=room_requests.id)`. This keeps a held partner out of the sweep's direct `unknown` transitions, whether or not the notice receipt has been saved yet. Keep the sweep in its current boot position; it neither reads the receipt file nor runs receipt listeners inside its transaction. Requests without pending hand-offs keep their existing restart treatment (`server/room-requests.ts:1340-1352`, `server/index.ts:16223`).

For held notices, retain receipt-first ordering and the separate stable owner-line write. After the existing cancellation check, look up the current receipt and paired request. For a non-terminal partner, call `settleReceipted` with the current receipt outside any outer transaction; if none exists, create the ordinary notice receipt instead. Do this before expiry/removal, including for an old room/shared hold newly excluded from the sweep. Only a completed partner may proceed to the existing expiry decision. A failed settlement leaves the held row for `stranded` and the next boot; do not expire or delete it in that attempt. Preserve terminal requests, cancellation precedence and `receipt.held` behavior; a held reply remains owned by its existing hold handling, not counted as a completed partner. The listener commits the receipt-derived request outcome and normal wake together. A second restart sees the terminal partner, skips re-entry and repeats only the stable owner notice if still held. For a direct hand-off, a successful individual receipt commit delivers its follow-up before later cleanup; a failed commit already registers a stranded retry (`server/delegations.ts:255`, `server/delegations.ts:598-633`, `server/delegations.ts:655-659`, `server/delegations.ts:1502-1533`, `server/delegations.ts:1663-1671`, `server/delegations.ts:1703-1719`, `server/index.ts:14583-14606`, `server/room-requests.ts:767-770`, `server/room-requests.ts:983-992`).

**Owner controls close the held pair atomically.** Re-read the held row and paired request inside the held-row removal transaction. Include partner completion in that transaction alongside the existing control/registration cleanup. Dismiss cancels a still-non-terminal partner before deletion. Send again settles the original partner from a usable current saved receipt, or cancels it, before queuing any new id; partner completion, old-row removal and a successful replacement queue commit together. Apply this rule to every removal branch, including `already_ran` and an unreadable payload. Preserve existing terminal outcomes, cancellation precedence and provider-evidence checks. Require actual partner terminality before deletion: receipt presence or a successful `settleReceipted` return is insufficient, since `receipt.held` does not complete a live partner. Completion failure, deferred settlement, a still-live partner or a rejected replacement queue must roll back the whole owner action, retaining the held row/control and queuing no new id; completion follow-ups wait for the outer commit. The existing `removeHeldRow` does not complete the partner, and the pair trigger excludes `phase='started'`, so neither currently enforces this rule (`server/delegations.ts:1678-1690`, `server/delegations.ts:1749-1779`, `server/delegations.ts:598-633`, `server/index.ts:14583-14606`, `server/room-requests.ts:767-770`, `server/pending-delegations-schema.ts:113-115`).

Not claimed: atomicity between the JSON receipt and SQLite, reversal of an already-terminal outcome from an older boot, or preservation against an existing ancestor-cancellation rule. A retained ordinary receipt can recover its non-terminal partner; an expired/pruned notice falls back to the held-row decision. Receipt presence alone neither proves provider execution nor prevents an explicit Send again. Existing evidence checks and owner choices still apply (`server/room-requests.ts:767-770`, `server/room-requests.ts:809-811`, `server/delegations.ts:438-444`, `server/delegations.ts:655-659`, `server/delegations.ts:1749-1772`).

For OWED, capture the already-loaded array reference and its length as a finite list of candidate IDs, without copying/filtering it. For each visited ID, call `findDelegationReceipt(id)` immediately before processing. Recheck the current receipt's `reply` and absence of a pending row; skip removed or acknowledged obligations and use the current version of a replaced receipt. Never pass the captured object to `settleReceipted`. Record creation can replace that object, and acknowledgement removes `reply` from the current object. A stale object could invoke the listener/wake again even if its message ID deduplicates the line. Newly added receipts do not extend this scan; their live settlement and stranded retry paths retain ownership (`server/delegations.ts:432-436`, `server/delegations.ts:483-489`, `server/delegations.ts:568-583`, `server/delegations.ts:655-659`, `server/delegations.ts:1641-1645`).

**Two small dependencies:** make the unloaded missing-message branch of `Store.patchMessage` execute `within` transactionally, matching the loaded missing-message branch; do not recreate the conversation. Also make `drainDelegations` return at entry while admission is held, before setting `drainingThreads`; successful completion supplies the boot wake. Gate waits return synchronously, but a long queue holds `drainingThreads` across page yields, making Stop unavailable during those yields. The early return prevents that long-queue case and unnecessary closed-gate walks (`server/store.ts:3852-3869`, `server/handoff-dispatch.ts:315-316`, `server/handoff-dispatch.ts:552-577`, `server/delegations.ts:1209-1229`, `server/delegations.ts:1244-1255`, `server/delegations.ts:819-825`).

**Ordering is decided:** per source conversation by rowid; per target/team by `(created_at,id)` with the existing continuation-wake priority and round-robin teams. A promised dispatch is awaited before the next item; a waiting item can remain queued while later admissible work proceeds. Preserve destinations and the shared dispatcher. No global serialization or cross-conversation completion order is introduced (`server/delegations.ts:228-230`, `server/delegations.ts:1231-1252`, `server/shared-work.ts:252-262`, `server/shared-work.ts:444-471`, `server/handoff-dispatch.ts:197`).

**Delivery boundary:** admission and the stamped start both honor the gate. Keep the existing prompt/start transaction, conditional stamp, duplicate in-flight guard and separately committed submission stamp. Submitted-without-evidence stays owner-held; accepted/evidenced work is not automatically submitted again. Send again creates a new identity after checking the original. These establish local identity/replay rules, not guaranteed exactly-once external execution (`server/handoff-dispatch.ts:189-226`, `server/handoff-dispatch.ts:315-323`, `server/handoff-dispatch.ts:429-449`, `server/delegations.ts:1475-1484`, `server/delegations.ts:1745-1771`).

## 4. Failures and closing rules

1. **SQL batch rollback or crash.** Only that SQL-only prefix rolls back; earlier commits remain. No new receipt file write or asker completion belongs to this transaction. Discard its callbacks, invalidate caches and keep its cursor. Retry with current predicates. Prove thrown failure and abrupt process exit (`server/database.ts:486-487`, `server/tx-scope.ts:15-24`, `server/store.ts:2644-2649`).
2. **Receipt persisted before SQL; restart or later cleanup.** Crash immediately after successful `saveReceipts` and before `settleReceipted` commits. On restart run the room sweep first: the held partner remains non-terminal, then the HELD pass settles from the saved receipt. Repeat the restart after settlement and prove no second completion/wake. Separately inject a later SQL-batch failure after a held room/shared notice: its partner stays terminal, capacity is freed and its committed wake remains. Fail the receipt's own commit in another case and prove same-process stranded retry; retain the direct hand-off wake case. Never treat the receipt alone as completion (`server/delegations.ts:483-489`, `server/delegations.ts:568-633`, `server/room-requests.ts:1340-1352`, `server/shared-work.ts:228-232`, `server/index.ts:14590-14606`).
3. **Stop or Dismiss during settle.** A synchronous unit finishes, then its yield lets the handler run. Re-read each next row/request; never restore a cancelled request. Dismiss cancels a live partner in the same transaction as held-row/control removal under section 3; a failed transaction leaves both intact. After an acknowledged Stop/Dismiss, that item cannot start through boot drain or an old retry. Owner/channel stop recovery remains separate (`server/delegations.ts:819-845`, `server/delegations.ts:1514-1533`, `server/delegations.ts:1775-1779`, `server/send-store.ts:791-802`).
4. **Arrivals and duplicate callbacks.** New hand-offs remain durably queued behind the gate. Send again completes the original partner atomically with removal and any replacement queue under section 3; it cannot open the gate. Shared reset keeps its captured ceiling; OWED keeps its finite candidate view. Duplicate settle requests share one job; final success releases one hold and runs ticket cleanup/drain once. Preserve existing queue order (`server/handoff-dispatch.ts:315-323`, `server/delegations.ts:1651-1660`, `server/delegations.ts:1767-1771`).
5. **Deleted source/target or missing notice.** Preserve tombstone and paired-request decisions; an absent registry entry alone is unresolved. Missing messages must still permit `within` cleanup, without creating a conversation. Unrelated rows continue (`server/handoff-dispatch.ts:193-209`, `server/handoff-dispatch.ts:332-342`, `server/delegations.ts:340-349`, `server/store.ts:3852-3869`).
6. **Large backlog and long units.** Bound root examinations by P and receipt-bearing work by one row per turn. Keep FULL. The new grouped transactions must meet section 6's duration gate; row-count bounds alone are not a latency guarantee. If SQL batching fails that gate, retain per-row commits for that path and leave the batching/performance acceptance unqualified. Keep the gate/retry/ticket-order corrections; do not relax durability, raise the budget or add an adaptive batching subsystem (`server/database.ts:280-282`, `server/db-busy.ts:108-115`).
7. **WAL pressure.** End transactions and release readers before yielding. Retain the off-thread PASSIVE checkpointer and autocheckpoint fallback. A pinned reader can retain WAL space; completion of a checkpoint is not the admission gate. Disk-full rolls back the affected SQL batch and uses automatic retry (`server/wal-maintenance.ts:6-16`, `server/wal-maintenance.ts:183-225`).
8. **Restart or restored data.** The next process starts from its own database and no prior cursor. Boot settle never calls restore release helpers, reimports quarantined pending work or grants release from a restore token. This lane adds no live-restore coordinator or generation protocol (`server/installation-restore-preparation.ts:380-392`, `server/restore-fence.ts:257-265`).
9. **Operational failure versus a deferred row.** Name the proposed local classifier `isBootSettleOperationalError(error)` in `server/delegations.ts`. Its explicit operational set is `isDatabaseBusy(error)`, `isNoSpaceError(error)`, Node `code` in `EIO`/`ENOMEM`/`EMFILE`/`ENFILE`, or a numeric SQLite `errcode` whose low byte is 6 (`SQLITE_LOCKED`), 7 (`SQLITE_NOMEM`), 10 (`SQLITE_IOERR`), 13 (`SQLITE_FULL`) or 14 (`SQLITE_CANTOPEN`), including extended codes. The existing helpers cover busy and `ENOSPC`/`EDQUOT` respectively; generic `ERR_SQLITE_ERROR`, arbitrary exception text and deterministic `ClassificationViolation` are not operational matches. Apply this classifier before deferring a thrown row error; outer BEGIN/COMMIT failures are unit failures independently of that set (`server/db-busy.ts:33-40`, `server/disk-space.ts:62-65`, `server/message-db.ts:1049-1055`, `server/message-db.ts:1095-1098`, `server/database.ts:472-487`).

   Retain the current maximum 20 busy attempts with asynchronous writer-gate waits and 100 ms to 2 s pauses for a unit. Busy exhaustion, another classified operational error or an outer BEGIN/COMMIT failure schedules the same unit automatically after 1 s, doubling to a 60 s cap; only one timer and one attempt may exist. Reset this outer delay after a successful unit, keep the hold/cursor through waits and stop the timer when the job completes or its database closes. Automatic retry continues at the capped rate until recovery or shutdown, as migration does; there is no human-action-only terminal state. These operational retry delays are distinct from the engineering round limits. Emit one `console.warn` per scheduled outer retry with phase, cursor, normalized error code, attempt and next delay; include no message content or raw exception payload. No user-visible stall alert is claimed (`server/delegations.ts:1613-1624`, `server/pending-delegations-schema.ts:323-344`, `server/handoff-dispatch.ts:552-577`).

An individual receipt/helper failure already represented as a retained non-runnable row and `stranded` obligation is a deferral, not failure of a new outer page. Preserve that behavior and continue past it; one failing completion hook must not block every conversation. Such a row is not counted as settled. The existing regressions explicitly require the scan to finish with that row retained, including when the first 100 rows fail (`server/delegations.ts:620-626`, `server/pm-sends-102-r28.test.ts:241-257`, `server/pm-sends-102-r29.test.ts:175-188`).

## 5. What the user sees

This revision removes the proposed preparation banner, progress counter, READY line and “Try preparation again” control. It needs no renderer files, snapshot/event additions or retry endpoint. Empty boots and the normal first-health wait show no new message. Headless boots recover through the automatic retry in section 4.9.

Use existing conversation controls: waiting messages retain Stop; held hand-offs retain Send again and Dismiss; expired/orphan controls disappear only with their committed cleanup. The app remains usable between units. Do not label examined items as sent or imply that opening the hand-off gate released owner/channel or restore-held items (`server/delegations.ts:819-825`, `server/delegations.ts:1663-1688`, `server/delegations.ts:1745-1778`).

No new user-facing copy is required. Inspect the existing controls in the isolated server workflow after implementation, including a missing notice and a Stop during the final yield.
