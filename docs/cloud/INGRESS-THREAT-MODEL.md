# Cloud home ingress

This describes the C3 candidate. Source, HTTP fixtures and launcher argument checks do not establish VM, kernel, provider or production qualification.

**Public edge.** Caddy is the only intended public listener. Its first block disables the admin API; a separate `murage-proxy` service has only `CAP_NET_BIND_SERVICE`, `NoNewPrivileges`, and a required dependency on the egress rules. Normal traffic goes over `/data/proxy/murage.sock` (`0660`, inside the setgid directory). `/hooks/*` instead goes to the loopback webhook ingress, which checks each endpoint's hashed secret and rate limit. Provider firewall qualification comes later.

**Request authority.** The main listener remains loopback. Every HTTP route first passes `cloudRequestAuth`; Host must name this home's public origin or loopback, and Origin must match for writes. Forwarded host and source IP are trusted only on the physically marked, configured Unix socket, never on TCP. Device sessions establish browser, phone or desktop scope; only actual loopback TCP peers have local service transport authority, still subject to the internal route's capability checks. Unauthenticated Unix proxy callers are anonymous: only public health and signed media byte reads pass, alongside the explicit pairing/bootstrap request handlers. Forwarded and desktop headers cannot create service or owner authority. Protected anonymous requests are refused before buffering their bodies. Sensitive actions require the bound additional confirmation. Revocation also closes streams and downloads.

**Upgrades.** The home-only upgrade handler applies the same auth and origin gate before dispatch. This batch has no WebSocket routes, so a permitted upgrade is still refused. Later login-relay routes must dispatch after this gate. The Unix listener mirrors the main upgrade handler.

**Process boundaries.** `murage` runs the server and supervisor after root startup, owns `/data/home` privately and holds the encrypted credential store. `murage-proxy` owns `/data/caddy` and reaches only the shared proxy socket. `murage-browser` has its selected bot's private browser directory, immutable browser binaries and its own sandbox; it has no sudo or turn-group membership. Engine commands run separately as `murage-turn` with only their selected home/workspace mounted. The constrained root launcher checks exact binary digests and stages trusted configuration read-only. Root performs enrollment, volume binding and firewall loading; the KEK stays in the controller and the unwrapped boot key travels only over a private pipe.

**Egress.** Non-root users cannot reach metadata or private/link-local networks except the explicit controller endpoint sets. Turn loopback is restricted to TCP 8799, whose internal routes still require their scoped capabilities. Browser loopback cannot reach 8799, 8800 or 2019. SMTP 25/465 is denied, 587 is limited and logged, and new connections have a per-UID meter. Egress failure blocks the home and proxy services. The labeled ext4 volume mounts with `nodev,nosuid` and stays root-owned; an unmarked nonempty volume is refused.

**Remaining qualification.** Native UID/DAC, namespace/daemon lifetime, Chromium sandbox, nftables enforcement, TLS/public firewall, pinned CLI policy precedence and upgrade/restore behaviour require their later authorized batches. Server compromise can reach engine credentials through the launcher; this boundary does not claim resistance to root compromise. Cloud profile cleanup uses durable usage ownership, including previous assignments, and fences browser admission until erasure is durably acknowledged. Its unit is an entire affected bot browser home; client confirmation must disclose the reset scope. Unknown legacy ownership is refused, and deterministic quarantines are retried without sweeping unrelated folders.
